# 운영 경험 개선 증분 — 행동 계약

작성 2026-09-01. 같은 날 적대 리뷰(finding 27건)의 결정을 반영해 개정했다 — 근거는 [`../docs/운영경험개선-증분-결정기록.md`](../docs/운영경험개선-증분-결정기록.md)에 있고, 이 문서가 정본이다. 이번 증분(적재 계약 강화·수집기 퇴역)의 행동 계약이며, v1 본체 계약([`001/spec.md`](001/spec.md))과 조회 표면 계약([`002/spec.md`](002/spec.md))은 이 문서가 명시한 지점 밖에서 무변경이다. 이 계약이 [`기획-입력.md`](../기획-입력.md)의 불변 결정과 어긋나면 기획-입력이 이긴다.

## 2. E0 — 전역 래퍼 배선 수정

현행: `~/.claude/settings.json`의 PreToolUse(matcher `Bash`) 훅이 `/Users/ian/.local/bin/uv run --project /Users/ian/workspace/reject-bench python -m rejectbench.wrapper …`를 부른다. `pyproject.toml:15`가 `package = false`라 프로젝트는 venv에 설치되지 않고, `python -m`은 호출 시점 cwd를 통해 패키지를 찾는다. **저장소 밖 cwd에서는 `ModuleNotFoundError`로 죽는다** — 실행으로 확인했다. 그동안 이 저장소 밖 세션의 가드 발동은 한 건도 기록되지 않았다.

계약:

1. 그 훅 명령에 인라인 `PYTHONPATH=/Users/ian/workspace/reject-bench` 접두를 넣는다. 명령의 나머지·타임아웃·matcher·다른 모든 훅 항목은 불변이다.
2. 전역 설정 편집은 스냅샷·롤백 절차를 거친다([`handoff.md`](handoff.md) 하드 게이트 5) — E4와 같은 절차다.
3. `docs/배선-목록.md`의 새 배선 표를 수정된 명령으로 갱신한다.
4. 이 배선이 고쳐지면 작업 트리의 `rejectbench/` 코드가 **모든 저장소의 모든 Bash 호출**에서 해석된다. E1·E2 편집 중 import 불가 상태는 전역에서 가드를 죽인다 — plan의 import 스모크가 이 위험을 받는다.

검증: 저장소 밖 cwd에서 `import rejectbench.wrapper` 성공 / 전역 설정이 유효 JSON / 훅 항목 수와 collect.py 항목 4건이 이 시점에는 그대로(E4가 지운다) / 래퍼 배선 잔존 — 읽기 조회로 확인하고 캡처를 `docs/배선-목록.md`에 남긴다.

## 3. E1 — 차단 사유 절단의 공백 구분 단위 보존

현행: 정제(명령 되풀이 제거 → 비밀 치환) 후 4000자 초과면 앞 4000자 + `…[truncated]` 맹목 절단(`recorder.py:245-246`). 절단점이 홈 경로·세션 ID 원문의 중간에 떨어지면 조각이 남고, 값 전체·공백 구분 단위만 보는 조회 경계가 그 조각을 인식하지 못한다.

**용어**: 이 절의 "공백 구분 단위"는 `str.split()` 경계다. "토큰"은 §5의 `\w` 경계 전용 용어로 남긴다 — 한 계약 안에서 두 정의를 섞지 않는다.

계약 — 절단점은 다음 순서로 정한다.

1. **공백 되물림**: 절단점이 공백 구분 단위를 반토막 낼 때만 앞 4000자 안의 마지막 **공백류**(개행·탭 포함) 앞까지 되물리고, 잘린 연속열은 통째로 버린다. 4000번째 다음 문자가 공백류면 단위가 경계에서 정확히 끝난 것이라 되물리지 않는다(2026-09-02 개정 — 개정 전 문면은 이 경우에도 온전한 단위 하나를 버렸다). 가드 stderr는 다중 줄이 흔하므로 개행도 경계다.
2. **민감값 가로지름 검사는 항상 돌린다.** 공백 되물림 뒤에도, 공백류가 하나도 없는 병리 입력에서도 적용한다. 절단점이 적재 시점에 아는 민감값 — **홈 절대 경로 원문**, **이 사건의 복합 세션 ID 원문**, **이 사건의 원본 세션 ID 원문** — 의 등장을 가로지르면 그 등장의 시작 전까지 되물리고, 되물린 새 절단점에도 같은 검사를 재적용한다(가로지름이 없어질 때까지 — 고정점). 개정 전 계약의 발동 조건("앞 4000자에 공백류가 하나도 없으면")은 **삭제한다** — 그 조건 때문에 공백을 품은 민감값을 공백 되물림이 정확히 반토막 내는 경로가 열려 있었다.
3. **하한 폴백**: 1·2를 거친 본문 길이가 **하한 미만이면 공백 되물림을 버리고**, 맹목 절단점에 2의 민감값 검사만 적용한 결과로 폴백한다. 폴백 결과에도 2의 고정점 검사가 적용된다.
   - **하한 = 본문 상한의 50%** (현행 상한 4000자 기준 2000자). 절대 문자 수가 아니라 **상한에 대한 비율**로 못 박는다 — 상한을 튜닝하면 하한이 함께 움직여야 하고, 두 상수가 따로 놀면 조용히 깨진다.
   - 근거: 공백 되물림은 정돈이고, 안전 보장(민감값 조각 미생성)은 폴백 경로도 그대로 유지한다. 앞 4000자의 공백이 5번째 문자면 저장 사유가 5자로 줄어 `insufficient_context`가 늘고, 이는 `기획-입력.md:70`이 "캡처 설계 실패"로 규정한 신호와 구별되지 않는다. 본문 절반 이상을 잃는 정돈은 하지 않는다.
4. 마커 `…[truncated]`와 본문 4000자 상한(마커 별도)은 유지한다. 되물림은 본문을 줄이기만 한다.
5. **내부 폴백**: 절단 계산이 예외를 던지면 현행 맹목 절단으로 되돌리고 **GuardEvent는 정상 기록한다.** 이 폴백은 `assemble_event` 안에서 닫혀야 한다 — 예외가 거기까지 새면 `recorder.py:286-299`가 `_record_loss`로 보내 LossRecord 강등(`recorded=False`)을 부른다. 기록기의 no-throw 봉투가 보장하는 것은 "가드 발동 결과 불변"이지 "기록 결과 불변"이 아니다. 관측창 중이라 사건 1건의 가치가 지금 최고다.
6. 정제 후 4000자 이하 입력의 저장값은 현행과 동일하다(회귀 없음).

**보장 범위**: E1이 막는 것은 **이 사건의 민감값 세 종에 한한** 새 파편 생성이다. 세 종은 공백 포함 여부와 무관하게 대상이다(2의 검사가 항상 돌기 때문). 세 종 밖의 값 — 대표적으로 **사유 텍스트에 섞인 타 세션의 ID**(transcript 파일 경로 등) — 은 대상이 아니다. 적재 시점에 알려면 store를 읽어야 하고, 그 I/O는 no-throw 봉투 안에서 감당하지 않는다.

**또한 이 보장은 값의 종류만이 아니라 적재 경로로도 한정된다** — `recorder.assemble_event`의 `GuardEvent.reason` 경로에만 있다. `judge.py:665-666`의 `PolicyVerdict.reason` 절단은 되물림 없는 맹목 절단 그대로이고, 판정 프롬프트가 `rubric.py:117`의 `target_path`(홈 절대 경로)와 `:120`의 사유 텍스트를 싣기 때문에 **같은 세 종의 새 파편을 계속 만들 수 있다**(실행으로 재현했다). 그 경로 수정은 이번 증분 범위 밖이다 — E1의 작업 대상은 `recorder.py`·`tests/test_recorder.py` 둘이다. 이 한계는 §5의 잔여 한계와 짝을 이룬다.

검증(red→green): 홈 경로가 4000 경계를 가로지르는 픽스처 / 복합 세션 ID가 가로지르는 픽스처 / **병리 입력(공백류 없음)에서 원본 세션 ID가 가로지르는 픽스처** / **공백을 품은 민감값이 가로지르는 픽스처(공백 되물림 뒤 검사가 도는지)** / **공백이 앞쪽 한 곳에만 있는 긴 입력(하한 폴백 발동)** / 공백 없는 병리 입력 일반 / 경계 정확히 4000자 / 짧은 입력 무변경 / 절단 경로 예외 주입 시 맹목 절단으로 기록 성공.

## 4. E2 — 세션 ID 적재 형식 규칙

저장 세션 ID는 복합값 `harness:원본`이다(실행 맥락 부재 시 `harness:unknown`).

1. **분해 규칙**: 첫 `:` 이전이 harness, **그 이후 전부**가 원본이다. `:`가 없는 값은 원본 부분이 없는 것으로 보고 이 절에서는 전체를 비준수로 분류한다. 이 분해는 **이 절의 형식 검사와 §5의 needle 산출이 같은 함수를 쓴다** — 자격 술어는 서로 다르지만(여기는 진단 술어, §5는 UUID 문법) 분해가 갈라지면 두 절이 다른 값을 본다.
2. **형식 검사는 원본 부분에만** 적용한다. 자리표시 경로(맥락 부재)는 검사 대상이 아니다.
3. **술어**: 길이 8~128, 문자집합 `[A-Za-z0-9_-]`. Claude Code 세션 ID(UUID, 하이픈 포함 36자)가 충족한다. 이 파라미터는 **명명 상수 한 곳**에 둔다. 변경은 사유 있는 계약 개정으로만 하며, 변경 시 UUID 준수 테스트와 §5 양성 대조를 재실행한다. 이 술어는 **E2 진단 전용**이고 E3 분류에 쓰지 않는다(§5) — 술어를 튜닝해도 E3 보장 범위는 바뀌지 않는다.
4. **필드**: `GuardEvent.session_id_format`. 값은 3상이며 직렬화 문자열은 정확히 아래 셋이다(다른 레코드 필드와 같은 lowercase snake_case StrEnum 관례).

   | 상태 | 직렬화 문자열 | 담기는 경우 |
   |---|---|---|
   | 준수 | `conforming` | 원본 부분이 3의 술어를 충족 |
   | 비준수 | `nonconforming` | 원본 부분이 술어 불충족, 또는 `:`가 없는 값 |
   | 미검사 | `unchecked` | 자리표시(맥락 부재) 신규 레코드 / 7.0 구형(필드 부재) / **검사 술어가 예외를 던진 경우** |

   `null`은 허용하지 않는다 — 신규 기록은 항상 셋 중 하나를 담는다. 필드명과 값 문자열은 이 계약이 고정한다(`records.py`의 키 집합 판정이 이 이름에 걸려 있다). 변경은 계약 개정으로만 한다.
5. **위반 시**: 기록은 그대로 진행한다 — 저장 세션 ID 값 불변, origin 규칙 불변, 가드 발동 결과 불변. 검사·표시가 기록 실패로 새면 안 된다.
6. **내부 폴백**: 검사 술어가 예외를 던지면 값은 `unchecked`이고 origin·저장 세션 ID·가드 결과는 불변이며 **GuardEvent는 정상 기록된다**(§3.5와 같은 이유). `unchecked`가 세 사유(자리표시·구형·검사 실패)를 합치는 것은 의도된 선택이다 — 진단력보다 사건 보존이 우선이고, 세 사유는 각각 `capture_status`·스키마 버전·손실 흔적으로 따로 남는다.
7. **스키마**: `SCHEMA_VERSION`을 `7.1`로 올린다. 인상은 **전역 상수 일괄**이라 7종 레코드 전부와 `judge.py:203` 사이드카 `JudgeCalibration`에 적용된다 — 새 필드가 없는 6종과 사이드카도 7.1로 찍힌다. 따라서 **7.1이라는 값은 어떤 코드 경로도 소비하지 않는 순수 표기**다: 구형 수용 판별은 버전 값이 아니라 **필드 부재** 기준이다. 보고서 헤더의 스키마 버전 줄 처리는 E7이 맡는다(§9).
8. **파서 완화**: 현행 `record_from_json`은 키 집합 완전 일치를 강제한다. 완화는 **`record_type == "guard_event"`이고 누락 키가 `session_id_format` 하나일 때만** 적용하며, 그 경우 `unchecked`로 읽고 손상 줄로 떨어뜨리지 않는다. 다른 필드 누락·다른 record_type은 여전히 손상 줄이다. 기존 저장 레코드는 한 건도 재작성하지 않는다(append 전용).
   - **실패 모드(완화를 빠뜨렸을 때)**: `_expected_keys`는 `_PARSERS[record_type]`별로 계산되므로 손상되는 것은 **`guard_event` 줄뿐**이다. 다른 6종은 멀쩡하다. 실제 피해는 "등록부 조회 실패"가 아니라 **운영 지표의 분모·사건 목록·검토 큐에서 사건이 통째로 사라지고 손상 줄 수만 늘어나는 것**이다 — 조용하고, 보고서상 사건 0건과 구별하기 어렵다.
9. **노출 범위**: 이 필드는 진단 용도다. E7이 `report.py`를 여는 것과 별개로 **이 검사 필드 자체의 보고서 노출 배선은 이번 증분에서 추가하지 않는다** — 술어를 명명 상수로 고정(3)하고 E3 자격을 술어에서 분리(§5)해 "보장 공집합" 최악 시나리오가 구조적으로 제거됐으므로, 비준수/미검사 건수를 세는 표면이 지금 필요하지 않다. E3의 가림 분류는 이 필드가 아니라 출력 시점의 모양으로 한다(§5) — 과거 레코드가 자동으로 같은 보장을 받게 하기 위해서다.

검증(red→green): UUID 준수 기록 / 7자·129자·금지 문자 비준수 기록 / `:` 없는 값 비준수 / 맥락 부재 자리표시의 `unchecked` / 검사 경로 예외 주입 시 값 `unchecked` + 기록 결과 불변 / **구 형식(7.0, `session_id_format` 부재) 저장 JSON 파싱 → `unchecked`로 적재, 손상 줄 0건** / **`guard_event`의 다른 필드 누락과 타 record_type의 필드 누락은 여전히 손상 줄**.

## 5. E3 — 조회 표면 가림 확장 (원문 0회 보장)

조회 표면의 출력 경계는 스냅샷의 저장 세션 ID들을 **출력 시점에, 값의 모양으로** 두 부류로 나눈다(저장 필드 무관 — 과거 레코드 자동 포함):

- **준수 복합값** — 원본 부분이 **UUID 문법**을 충족: 값 전체·완전한 토큰은 물론 **단어-속-포함(임의 부분문자열 등장)**까지 같은 별칭으로 치환한다. **원본 부분 단독 등장도 같은 별칭으로 치환한다** — 세션의 원본 ID는 transcript 파일 경로 등으로 사유 텍스트에 복합 접두 없이 나타날 수 있고, "원문 0회"는 식별자의 원문 자체를 뜻하기 때문이다(needle = 복합값과 그 원본 부분, 동일 별칭). 이 부류에 한해 응답 원문 0회를 보장한다.
- **그 외** — 자리표시(`harness:unknown`), UUID 문법 비충족 값, `:` 없는 값: 현행 값 전체·완전한 토큰 매칭을 유지한다. `unknown` 같은 일반 단어와 짧은 값이 일반 텍스트를 훼손하지 않게 하기 위함이다.

**자격은 §4 술어가 아니라 UUID 문법이다.** §4의 형식 술어(8~128, `[A-Za-z0-9_-]`)는 E2 진단 전용으로 유지하고 이 분류에 쓰지 않는다. 그 술어로는 `2026-09-01`(10자, 허용 문자집합 충족)이 준수로 분류되고, 그러면 무경계 부분문자열 치환이 응답 전체의 `occurred_at`·`content_hash`·`event_id`를 별칭으로 뭉갠다 — `002/spec.md:72`가 명시적으로 닫았던 구멍의 재개방이다. 실데이터는 100% UUID(Claude Code 세션 ID)이고 Codex는 가드 발동 배선이 범위 밖이라 **좁혀도 배제되는 실제 대상이 없다**. 탈락한 값은 보호를 잃는 게 아니라 "그 외" 부류의 토큰 경계 매칭(002 수준)으로 떨어진다 — 안전 방향 실패다. 자격이 술어와 분리되므로 §4 술어를 튜닝해도 이 보장 범위는 변하지 않는다.

유지되는 002 계약(무변경): 별칭은 응답 안에서만 유효 / 별칭↔원문 매핑 비저장 / 고정 JSON 키 불변 / 홈 치환 전 별칭화 선행 / 긴 needle 우선 매칭 / 별칭 재치환 방지 / 일반 값이 ID와 우연히 겹치면 비노출 우선 / 오류 경로 포함 모든 레코드 유래 문자열이 경계를 정확히 한 번 통과.

코너 규정: 서로 다른 준수 복합값이 같은 원본 부분을 공유하는 경우(세션 정의상 실운영에서는 나오지 않고 픽스처만 만들 수 있는 형태) 그 원본 단독 등장은 비노출 우선으로 그중 한 복합값의 별칭으로 치환한다 — 가려짐은 보장하고, 어느 별칭인지는 보장 대상이 아니다.

남는 한계(계약 명시로 남긴다 — 별도 태스크 없음):

- 완전한 ID가 아닌 **조각**(과거 절단이 만들었을 수 있는 파편)은 매칭 대상이 아니다. E1이 적재 시점에 **이 사건의 민감값 세 종에 한해** 새 파편 생성을 막는 것으로 대응한다(§3 보장 범위). 타 세션 ID의 파편과, **판정 사유(`PolicyVerdict.reason`) 적재가 만드는 이 사건 세 종의 파편**은 여전히 남을 수 있다 — E1의 되물림은 `recorder`의 적재 경로에만 있고 `judge.py:665-666`은 맹목 절단 그대로다(§3 보장 범위).
- **UUID 문법 비충족 세션 ID의 원본 부분 단독 등장은 별칭 대상이 아니며 원문으로 나갈 수 있다.** 이건 조각이 아니라 완전한 식별자의 원문 노출이다 — 일반 텍스트 훼손 회피를 위한 의도적 선택이며, D4로 "그 외" 부류가 커졌으므로 더 중요해진 한계다.
- 이 잔여 한계는 이 계약과, E6의 정본 갱신(모듈 규칙의 비노출 서술)에 반영한다.

검증(양성 대조 — 하드 게이트): UUID 문법 준수 ID를 **일반 단어 속에 파묻어** 심은 픽스처로 도구 3종 + 오류 경로의 응답 전체에서 원문 0회를 확인한다. 값 전체·온전한 토큰 픽스처, 자리표시·비준수 ID 주변 텍스트의 비훼손 검증을 병행한다. **준수 ID가 타임스탬프·`content_hash`·`event_id`와 겹치는 픽스처에서 그 값들이 변하지 않음**을 확인한다. 깨끗한 픽스처의 깨끗한 출력은 증거가 아니다. 재현·실기동 확인은 임시 store로만 한다.

## 7. E5 — 관찰 프로토콜 추기

`docs/관찰-프로토콜.md` "변경 기록" 절에 append(덮어쓰기·기존 본문 수정 금지). 모든 항목은 일자·사유를 달고 사건 정의·출처 규칙·평가 양식·종료 조건이 불변임을 명시한다.

1. **기준선 이월 규칙**: 측정 전 해당 세션의 대화 기록이 소멸했으면 그 사건의 기준선은 포기하고 다음 자연 사건으로 이월하며 사유를 남긴다(2026-09-01 사용자 결정 — 시점 탓에 도구 쪽이 유리해지는 왜곡 방지).
2. **기구 변경 기록**: **E0·E1·E2·E4**가 관측창 내 기구를 바꿨다 — E0은 전역 래퍼의 실제 도달 범위를, E1·E2는 적재 계약을, E4는 PermissionRequest·PermissionDenied 수집을 전역에서 제거한다. 일자·사유와 함께, 측정 의미(사건 정의·출처 규칙·평가 양식)는 불변임을 명시한다. E0의 범위 효과는 4가 따로 받는다.
3. **관측 무대 변화**: 1차 관측 무대였던 reply-gate 배포 잔여 작업은 진행되지 않는다(reply-gate 완성 — 사용자 2026-09-01 확인). 자연 발동 기대는 전역 가드 중심이 된다. **귀결로 `protect-live-reports`의 관측 기대 발동은 0에 수렴하며, 판정 가능 가드 성립이 사실상 `block-dangerous-git` 단독에 의존한다**는 점을 명기한다.
4. **관측 범위 소급 정정**: 2026-08-29(관측창 오픈)~E0 완료일 구간은 선언된 범위(`관찰-프로토콜.md:11` "Claude Code가 도는 모든 저장소 세션")보다 좁게, 사실상 reject-bench 세션만 돌았다. 선등록 정본이 그 구간에 대해 거짓이었다는 사실을 그대로 적는다.
5. **자기차단 산입 규칙**: `GuardEvent.project == "reject-bench"` 발동은 산입하되 별도 표기하고 지표를 두 벌 낸다. `관찰-프로토콜.md:44`의 기존 선례("관측 도중 새 가드 등록 사건은 별도 표기하고 기존 지표와 섞지 않는다") 형식을 따르며 새 메커니즘을 발명하지 않는다. 계산은 E7이 맡는다(§9).
6. **본문 vs 변경 기록 승자 규칙**: **본문과 변경 기록이 어긋나면 변경 기록이 이긴다.** 이 문장 자체를 변경 기록 안에 둔다 — 본문에 넣으면 append-only(하드 게이트 6)와 충돌한다. 4의 범위 정정이 정확히 이 메커니즘으로 작동한다.
7. **이월 누계 표기**: 이월할 때마다 사건 식별과 소멸 사유를 남기고, 누계를 종료 보고서에 표기한다.
8. **ADR 0001 supersede**: 1차 관측 무대 취소가 [`../docs/adr/0001-관측대상-실존-가드-앵커.md`](../docs/adr/0001-관측대상-실존-가드-앵커.md)를 어디까지 대체하는지 적는다. 3의 귀결(`protect-live-reports` 기대 발동 0 수렴, 판정 가능 가드가 `block-dangerous-git` 단독 의존)이 ADR 0001이 전제한 무대 구성을 바꾼다.

## 9. E7 — 보고서 파티션

D2의 "지표 두 벌"을 사람이 세지 않고 도구가 계산한다. `report.py:10`이 이미 가르는 **시험/운영 분리 안쪽**에서, 운영 사건을 다시 도구개발/그-외로 가른다. 대표 주장이 자기생성 증거에 얹히는 것을 막기 위함이다(`docs/adr/0001-관측대상-실존-가드-앵커.md:11`이 "관측하려고 가드를 만들었다"는 순환을 이미 기각했다).

1. **파티션 키**: `GuardEvent.project == "reject-bench"` → **도구개발**, 그 외 → **그-외**. `project`는 `GuardEvent`·`GuardSpec`에만 있는 필드이며, 이 사실이 적용 범위의 상한이다.
   - **알려진 한계(2026-09-02 코드리뷰, 사용자 결정)**: `project`는 훅 payload의 **cwd basename**이다(`recorder.py` `Path(cwd).name`). cwd가 이 저장소의 하위 디렉터리(`…/reject-bench/docs` → `docs`)거나 basename이 다른 워크트리·클론이면 도구개발 자기차단이 **그-외로 분류된다**. 반대로 무관한 저장소가 우연히 `reject-bench`면 도구개발로 들어간다. 관측창 중에는 기록기를 고치지 않는다(모든 저장소의 Bash 훅에서 도는 코드). **O2 종료 판정에서 그-외 사건의 `project` 값을 수동 확인**한다 — 그-외 대표값이 성립했을 때 근거 사건이 실제 다른 저장소인지 보는 절차다. 기록 규칙 변경은 다음 주기.
2. **적용 범위 — 운영 사건 집합(`operation_event_ids`)에서 파생되는 지표 전부.** "대표 지표만"이라는 임의의 선을 긋지 않는다:
   - 정책 불일치율, 불필요 차단율, 불일치율, `correct_but_unnecessary`, `incorrect_but_useful`
   - 운영 사건 수
   - 판정·검토의 미처리/보류 현황(건수와 최장 경과)
   - 증거 기반 결정 완료율
3. **적용하지 않는 것** — 파티션 키가 없거나 단위가 운영 사건이 아니다:
   - 손실·정정·강등 수, 손상 줄 수, 총 레코드 수 (해당 레코드 5종에 `project`가 없다)
   - 시험/unknown/unregistered 출처 집계 (운영 사건이 아니거나 기존 분리의 바깥)
   - 기준선·판정기 교정 사이드카
   - **가드별 표는 이미 `project` 열을 가지므로 그 열이 판별자다** — 열을 중복 추가하지 않는다.
4. **표기**: 각 지표에 전체·도구개발·그-외 세 값을 병기하고, **대표값은 그-외**임을 보고서 문면에 적는다. 분모 0은 파티션 안에서도 `미검증`이며 성공이 아니다.
5. **합산 검산 금지**: 사건 단위 지표의 원수는 두 벌의 합이 전체와 같지만, **결정 완료율은 가드 단위라 합이 성립하지 않는다** — 한 가드가 전체에서는 판정 가능(서로 다른 2세션)이면서 어느 파티션 안에서도 판정 불가일 수 있다. 합으로 검산하지 않는다.
6. **분자⊆분모**는 각 파티션 안에서 독립적으로 성립해야 한다(`Ratio.__post_init__`가 강제한다). 지표 정의는 `metrics`의 단일 정의를 그대로 재사용하고 이 모듈에서 재정의하지 않는다.
   - **파티션 안 근거만 인정한다(2026-09-02 명문화, 사용자 결정)**: 파티션 위에서 잰 결정 완료율은 결정의 근거 사건(`evidence_event_ids`)이 **전부 그 파티션 안**에 있고 그 안에서 2세션 이상일 때만 "결정됨"으로 센다. 근거가 두 파티션에 걸친 결정(도구개발 ev + 그-외 ev)은 그-외에서 **미결정**이다 — 자기차단 사건이 근거의 일부여도 그-외 대표값에 기여하면 D12가 막으려는 순환이 다시 열린다. 구현은 `metrics.decision_completion`의 `evidence ⊆ guard_decidable`이며 이미 그렇게 동작한다. 그-외 대표값을 성립시키려면 결정을 그-외 사건만으로 근거를 대야 한다.
7. **스키마 버전 헤더**(§4.7의 귀결): 헤더의 스키마 버전 줄은 **기록기 현행 버전**과 **스냅샷에 실제로 존재하는 버전 집합**을 함께 낸다. 둘이 같으면 한 값만 렌더링한다. 7.0/7.1이 섞인 store에서 코드 상수 하나만 찍으면 그 줄이 데이터가 아니라 코드 버전을 말하게 된다.
8. 비노출 계약(홈 경로·세션 식별자 미기재, 사건 id·enforcement 경로·guard_hint 미렌더링)은 파티션 추가 후에도 그대로다. `project` 값은 이미 가드별 표에 렌더링되고 있으므로 새 노출이 아니다.

## 10. 검증 게이트

- 전체 게이트는 `uv run pytest` 하나다(연속성 회귀 포함). 새 행동은 red→green으로 만든다.
- 테스트는 임시 디렉터리 store만 쓴다. 운영 `data/`에 닿으면 기존 autouse 게이트가 하드 실패시킨다 — 게이트를 끄거나 완화하지 않는다. 네트워크 금지.
- **기준선 측정이 선행되므로 빌드 중에는 조회 금지가 해제된 상태다.** 다만 E3의 재현·실기동 확인은 **테스트 격리 목적으로** 여전히 임시 store로만 한다 — **`.mcp.json` 등록 서버가 아니라 `--store <임시 경로>` 인자로 별도 기동한 프로세스**를 쓴다. `REJECTBENCH_STORE` 환경변수는 기록기 전용이라 서버에 통하지 않으며, 인자 없는 기동은 조용히 운영 store를 읽는다.
- E0·E4의 전역 설정 편집은 스냅샷·롤백 절차를 거치고, 읽기 조회 캡처를 `docs/배선-목록.md`에 남긴다.

## 11. 우선순위

기준선 측정(선행 절차) → **E0 → E1 → E2 → E3 → E4 → E5 → E6 → E7**.

E0은 관측 자체를 고치므로 맨 앞이다 — v0 수집기는 직접 경로라 지금 모든 저장소에서 작동하고 v7 래퍼만 무동작이므로, E4를 먼저 하면 **작동하는 관측자를 먼저 걷어내고 고장난 것만 남는 구간**이 생긴다. E1→E2→E3(적재 계약 강화 묶음)이 핵심이며 이 순서다. E4는 독립 정리, E5·E6·E7은 마무리다. 어느 하나가 막히면 나머지는 그대로 완수하고 막힌 것만 보고한다.
