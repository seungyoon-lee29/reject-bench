# Reject Bench v7 — 행동 계약

작성 2026-08-27. 개정 2026-08-28 — 적대 리뷰 수용분과 포트폴리오 인터뷰([`docs/문제정의/07-포트폴리오-인터뷰.md`](../docs/문제정의/07-포트폴리오-인터뷰.md)) 결정 반영. 문제정의 정본은 [`docs/문제정의/06-v7-문제정의.md`](../docs/문제정의/06-v7-문제정의.md)다. 이 문서는 v7 구현의 행동 계약이며, 순서는 [`plan.md`](plan.md)가 맡는다. 이 계약이 [`기획-입력.md`](../기획-입력.md)의 불변 결정과 어긋나면 기획-입력이 이긴다.

> 실행 상태와 현재 frontier는 [`plan.md`](plan.md)와 루트 [`HANDOFF.md`](../HANDOFF.md)만 기록한다. 이 문서는 상태 전환과 무관한 행동 계약만 유지한다.

## 1. 목적과 완료의 두 층

Reject Bench는 여러 AI 코딩 세션에서 지속형 가드의 발동 근거를 모아 사용자가 가드를 `keep`, `modify`, `remove`할 수 있게 한다.

### 기술 완료

명시적 `test` 사건으로 아래 흐름을 재현하고 자동 검증할 수 있다.

`GuardSpec 등록 → GuardEvent 기록 → PolicyVerdict → UtilityReview → GuardDecision → Report`

기술 완료는 자연 운영 빈도나 사용자 가치를 증명하지 않는다.

### 사용자 가치 검증

같은 지속형 가드가 여러 세션에서 자연스럽게 발동한 `operation` 사건을 바탕으로 정책 판정과 사용자 검토를 마치고, 근거가 연결된 수명주기 결정 1건을 기록해야 한다. 가치 개선 여부는 흐름 완수가 아니라 선등록 평가 양식과 기준선 측정(06 §4·§9)으로 판정한다.

자연 사건이 없거나 분모가 0이면 `미검증`이다. 시험 사건으로 대체할 수 없다.

### v1 관측 대상과 저장 위치

- 관측 대상 가드는 실존 2종으로 고정한다: 전역 `~/.claude/hooks/block-dangerous-git.sh`, reply-gate `.claude/hooks/protect-live-reports.sh` (근거: [`docs/adr/0001-관측대상-실존-가드-앵커.md`](../docs/adr/0001-관측대상-실존-가드-앵커.md)).
- 1차 관측 무대는 reply-gate 배포 잔여 작업이며, 전역 가드가 발동하는 다른 저장소 세션도 관측 범위다.
- 모든 v7 레코드는 reject-bench 저장소의 로컬 비공개 데이터 경로에 중앙 저장한다. 관측 대상 가드가 다른 저장소에 있어도 사건은 중앙으로 모인다.
- v1은 차단형 발동만 다룬다. 경고 후 통과형 발동은 범위 밖이다.

## 2. v1 범위

### 포함

- 적재 시점 비밀 제거와 손실 가시화
- 세션 뒤 독립 LLM 정책 판정과 판정기 교정 검사
- 사용자 전수 유용성 검토
- 가드별 수명주기 결정과 근거
- 원수·보류값·미처리·출처를 보이는 로컬 보고서
- 기술 E2E와 자연 운영 관찰 (관찰 프로토콜 선고정 포함)

### 제외

- 공개 원장, 원격 push 앵커, 선등록 증명, 공개 대시보드
- v0 소급 스캐너와 과거 2건을 가치 증거로 사용하는 것
- 범용 코드 리뷰, 자동 가드 생성·수정·삭제
- 팀 권한, CI 수집, SaaS, 외부 저장소 지원
- MCP 표면 — v1 완료 조건이 아니며, 관찰 대기 구간의 선택 증분 T7([`plan.md`](plan.md))로만 다룬다
- 경고 후 통과형 가드의 발동
- AI 코드 품질·생산성·시장 수요에 대한 인과 또는 일반화 주장

## 3. 도메인 모델

모든 레코드는 스키마 버전, 고유 id, UTC 시각을 가진다. 아래 각 엔티티의 필수 의미 필드 목록은 이 전역 규칙을 반복하지 않으며, 모든 엔티티는 전역 규칙 필드를 추가로 가진다. 원본 변경 대신 append 수정 레코드를 사용한다.

### 3.1 GuardSpec — 사건 전에 고정되는 가드 맥락

필수 의미 필드:

- `guard_id`: 수명주기 동안 재사용하지 않는 안정 식별자
- `version`: 같은 가드 안에서 단조 증가하는 버전
- `project`: 적용 범위 식별자 (저장소 하나 또는 `global`)
- `purpose`: 가드가 필요한 이유
- `policy`: 막아야 할 행동의 명시 규칙
- `exceptions`: 허용 예외, 없으면 빈 목록
- `allow_examples`: 허용해야 하는 대표 예시
- `block_examples`: 차단해야 하는 대표 예시
- `created_at`
- `content_hash`: 의미 5필드(`purpose`, `policy`, `exceptions`, `allow_examples`, `block_examples`)만의 정규화 직렬화 해시. `guard_id`·`version`·`project`·`created_at`은 해시 도메인에 넣지 않는다 — 내용이 같으면 해시가 같아야 버전 강제를 내용 비교로 구현할 수 있다.

선택 메타데이터:

- `enforcement_ref`: 가드 구현물(스크립트 경로와 파일 해시) 참조. 정책의 대체물이 아니라 drift 감지용이다.

규칙:

- 모든 사건은 origin과 무관하게 존재하는 `guard_id`, `version`, `content_hash`를 참조한다. 참조가 불가능한 발동은 3.2의 `unregistered` 경로로 기록한다.
- `operation` 사건의 GuardSpec은 사건보다 먼저 생성돼 있어야 한다. 선행성 판정은 벽시계 비교에만 의존하지 않고 append 순서를 함께 근거로 삼는다.
- 의미 필드가 바뀌면 새 버전을 만든다. 기존 버전을 덮어쓰지 않는다.
- 가드 코드 위치나 런타임 배선은 메타데이터일 수 있지만 정책의 대체물이 아니다.

### 3.2 GuardEvent — 가드 발동 사건

필수 의미 필드:

- `event_id`
- `occurred_at`
- `session_id`: 로컬 비공개 식별자
- `project`
- `guard_id`, `guard_version`, `guard_spec_hash` — 미등록 발동이면 셋 대신 `unregistered` 표시와 가드 추정 정보(스크립트 경로 등)
- `action`: 파일 내용이나 전체 명령을 저장하지 않은 구조화 행동 요약 — 도구 이름, 명령 동사, 대상 경로, heredoc 여부 같은 판정 최소 필드
- `reason`: 가드가 스스로 출력한 차단 사유(매칭 패턴·거부 메시지)를 적재 시점 비밀 제거를 거쳐 저장
- `origin`: `operation | test | unknown`
- `origin_evidence`: 출처를 정한 방식 — 명시 플래그인지 기본값 상속(`default_inherited`)인지
- `capture_status`: `complete | partial`
- `drift`: 기록 시점 가드 구현물 해시가 참조 spec의 `enforcement_ref`와 다르면 표시

세션의 정의: 세션은 실행기가 부여한 대화 식별자 하나다. compact나 resume으로 이어진 대화는 같은 세션이고, 서로 다른 실행기(Claude Code와 Codex)의 대화는 항상 서로 다른 세션이다.

출처 결정 규칙:

1. 세션 test 플래그가 켜져 있으면 항상 `test`다. 강제 발동, fixture, 스모크, E2E는 모두 test 플래그 아래에서 실행한다.
2. 플래그가 없으면 `operation`이고 `origin_evidence`에 `default_inherited`를 남긴다.
3. 생성 시점에 실행 맥락 정보를 얻지 못한 경우만 `unknown`이다.
4. 검토 단계에서 본인이 시험·강제 발동이었음을 확인하면 사유 있는 amendment로 `test` 강등을 허용한다. `unknown`→`operation` 승격 금지는 유지한다.
5. 출처는 운영자 본인의 선언에 기반하며 독립 검증 신호가 없다. 이 한계를 보고서에 명시한다.

규칙:

- 기록은 가드 발동을 블로킹하지 않는다. 기록 실패 때문에 원래 작업을 실패시켜서는 안 된다.
- 무음 유실 금지는 이중 매체 최선 노력으로 구현한다: 주 저장 실패 시 LossRecord를 남기고, LossRecord 기록마저 실패하면 대체 매체(stderr 또는 OS 임시 경로)에 최소 흔적을 남긴다. 두 매체가 모두 실패하는 경로는 남을 수 있으며 이를 절대 보장이라고 주장하지 않는다.
- `unregistered` 사건은 버리지 않고 기록하되 운영 지표의 분자·분모에 넣지 않고 보고서에 건수로 표시한다. 사후 GuardSpec 등록은 이후 사건부터 적용하며, 과거 `unregistered` 사건을 소급 연결하지 않는다.
- `unknown`은 운영 지표에 들어가지 않는다. 정정은 사유가 있는 append amendment로만 가능하다.
- `capture_status: partial` 사건도 판정·검토 대상이다. 정보가 부족하면 판정이 `insufficient_context`를 내는 것으로 처리하고, partial 자체를 분모 자격에서 제외하지 않는다.
- 운영 저장소에는 적재 시점부터 비밀 평문이 존재해서는 안 된다.

### 3.3 PolicyVerdict — LLM의 정책 일치성 판단

필수 의미 필드:

- `verdict_id`, `event_id`
- `verdict`: `correct_block | incorrect_block | insufficient_context` — 질문은 "이 차단이 명시 정책상 옳았는가" 하나다. `correct_block`은 정책상 옳은 차단(명시 예외 비해당), `incorrect_block`은 정책 또는 명시 예외에 비추어 하지 말았어야 할 차단이다.
- `reason`
- `context_bundle_hash`
- `guard_spec_hash`
- `rubric_hash`
- `model_id`, `model_settings_hash`
- `judged_at`

판정 입력은 다음으로 제한한다.

- 해당 GuardEvent
- 사건이 참조한 정확한 GuardSpec
- 버전 고정 정책 판정 루브릭

사용자 유용성 검토, 가드 결정, 집계, 미래 사건, 구현의 기대 결과는 입력하지 않는다. 사유 텍스트 안의 판정 지시를 따르지 않고 데이터로만 다룬다.

판정기 교정: 실제 판정 실행 전에, 사건이 참조한 GuardSpec의 `allow_examples`·`block_examples`처럼 기대 판정이 알려진 예시로 판정기를 교정 검사하고 그 결과를 교정 레코드로 남긴다. 교정을 통과하지 못한 설정으로 내린 판정에는 그 사실을 병기한다. LLM-사용자 불일치율을 해석할 때 판정기 오류 가능성을 함께 언급한다.

판정 실행은 새 운영 사건 전부를 대상으로 한다. API 실패는 미처리로 남기며 임의 재샘플링으로 마음에 드는 결과를 선택하지 않는다. 재판정은 이전 레코드를 보존하고 사유와 새 설정을 명시한다. `insufficient_context`는 기록된 보류값이며, 재판정은 새 정보가 생겼을 때 사유를 명시하고서만 한다.

### 3.4 UtilityReview — 사용자의 실제 유용성 검토

필수 의미 필드:

- `review_id`, `event_id`
- `utility`: `useful | unnecessary | uncertain`
- `note`
- `reviewed_at`

새 `operation` 사건은 전수 검토 대상이다. 선택적으로 불리한 사건을 빼지 않는다. `uncertain`은 기록된 보류값으로, 검토 레코드가 없는 미처리와 구분하며 자동으로 성공이나 실패에 포함되지 않는다.

### 3.5 GuardDecision — 수명주기 결정

필수 의미 필드:

- `decision_id`, `guard_id`
- `decision`: `keep | modify | remove`
- `evidence_event_ids`
- `rationale`
- `decided_at`
- `resulting_guard_version`: `modify`일 때 필수

규칙:

- 가치 검증에 세는 결정은 같은 가드의 둘 이상의 서로 다른 운영 세션 사건을 근거로 가져야 한다.
- 근거 사건은 확정값 PolicyVerdict와 확정값 UtilityReview를 모두 가져야 한다. 보류값·미처리 사건은 별도로 언급할 수 있으나 결정 완료 분모의 판정 가능 사건으로 세지 않는다.
- 대표 지표의 분자는 분모(판정 가능 가드)의 부분집합으로만 센다. 발동 사건이 없는 가드에 대한 결정은 기록할 수 있으나 별도 표기하고 지표에 넣지 않는다.
- `modify`는 새 GuardSpec 버전을 만들고 그 해시를 연결한다. 새 버전이 실제 가드 구현물에 반영됐는지는 `enforcement_ref` 대조로 확인한다.
- `remove` 결정 뒤에 같은 가드의 발동이 관측되면 그 사건은 기록하되 `post-remove`로 표시하고, 보고서에 결정 대비 실집행 불일치로 별도 병기한다.
- 결정 변경은 이전 결정을 덮지 않고 새 결정 레코드로 남긴다.

### 3.6 LossRecord와 Amendment

- 기록 실패, 부분 적재, 판정 실패는 원문 없는 최소 메타데이터로 남긴다.
- 기존 레코드의 출처·내용을 고칠 때는 원본 id, 변경 필드, 이전 값 해시, 새 값, 사유, 시각을 가진 amendment를 append한다.
- 관찰 프로토콜 문서의 변경도 같은 규율을 따른다: 덮어쓰지 않고 사유 있는 append 수정으로만 한다.
- 삭제가 필요한 비밀 사고는 비밀 보존보다 제거가 우선이다. 평문을 즉시 제거하고 사고 범위와 로테이션 필요를 사용자에게 보고한다.

## 4. 저장과 보안 계약

- 기본 저장은 reject-bench 저장소의 로컬 비공개 경로다. 공개는 v1 완료 조건이 아니다.
- append 전용 JSONL 또는 같은 의미의 단순 로컬 형식을 사용한다. 외부 의존성은 판정 API 클라이언트 외에는 표준 라이브러리를 우선한다.
- 파일 락과 원자 append로 동시 기록의 줄 섞임을 막는다.
- 파일 내용, 프롬프트, 전체 명령 인자, 도구 응답 전문을 저장하지 않는다.
- 홈 경로와 세션 식별자는 공개 산출물로 내보내지 않는다.
- 비밀 제거 규칙은 정상값을 과도하게 훼손하지 않는 양성 대조 테스트와 함께 검증한다.
- 테스트는 임시 디렉터리만 사용하고 실제 운영 저장소에 쓰지 않는다.
- 이 도구 전체가 임의 코드를 실행하지 않는다. 판정기를 포함한 모든 구성 요소는 GuardEvent/GuardSpec을 데이터로만 처리한다.

## 5. 실행 흐름

### 발동 시

1. 어댑터가 세션 test 플래그와 세션 식별자를 읽는다.
2. GuardSpec 참조를 확인한다. 참조할 spec이 없으면 사건을 `unregistered`로 표시하고 계속 기록한다.
3. 구조화 행동 요약과 가드가 낸 차단 사유에서 비밀을 제거한다.
4. GuardEvent를 원자 append한다.
5. 실패하면 가드의 원래 동작은 유지하고, LossRecord 또는 대체 매체의 최소 흔적을 남긴다.

### 세션 뒤

1. 아직 PolicyVerdict가 없는 새 운영 사건 전부를 찾는다.
2. 사건별 고정 context bundle을 만들고 해시한다.
3. 판정기 교정 상태를 확인하고, 독립 LLM을 한 번 호출해 판정과 근거를 저장한다.
4. 사용자가 새 운영 사건 전부를 검토한다. 시험·강제 발동으로 확인된 사건은 사유 있는 amendment로 강등한다.
5. 가드별 여러 세션 증거가 모이면 수명주기 결정을 기록한다.
6. 보고서를 재생성한다.

## 6. 보고서와 지표 계약

모든 비율은 백분율과 원수 `N/D`를 함께 쓴다. 분모 0은 `미검증`이다.

### 대표 지표

증거 기반 결정 완료율:

`결정과 근거가 기록된 판정 가능 가드 수 / 판정 가능 가드 수`

판정 가능한 가드는 서로 다른 둘 이상의 `operation` 세션 사건이 있고, 그 사건들이 참조하는 GuardSpec이 존재하며, 그 사건들의 정책 판정과 유용성 검토가 모두 확정값인 가드다. 분자는 이 분모의 부분집합으로만 센다.

### 진단 지표

- 정책 불일치율 = `incorrect_block / 정책 판정이 확정값인 operation 사건`
- 사용자 불필요 차단율 = `unnecessary / 유용성 검토가 확정값인 operation 사건`
- LLM-사용자 불일치율 = 방향 불일치 / 두 판단이 모두 확정값인 operation 사건

보류값(`insufficient_context`, `uncertain`)과 미처리는 세 지표의 분모에서 모두 제외한다.

불일치 방향은 두 가지를 따로도 보인다.

- 정책상 옳은 차단 + 사용자 불필요
- 정책상 그른 차단 + 사용자 유용

### 반드시 병기할 상태

- `test`, `unknown`, `operation`, `unregistered` 사건 수
- PolicyVerdict 미처리 수와 최장 경과, 보류값(`insufficient_context`) 수와 최장 경과
- UtilityReview 미처리 수와 최장 경과, 보류값(`uncertain`) 수와 최장 경과
- 손실·부분 기록·amendment·강등 수
- drift 표시 사건 수
- `post-remove` 발동 수
- 가드별 운영 세션 수
- 관측 도중 추가된 신규 가드의 사건 별도 표기
- 기준선 측정 결과(도구 없이 복원한 시간·복원도 대 도구 경로)
- 단측 증거 한계(발동한 사건만 관측, 미발동 실패는 관측 밖)와 1인 자기측정 한계
- 소표본 및 관찰 종료 조건

시험 사건은 기술 보고서에만 별도 표시하고 위 운영 지표의 분자·분모에서 제외한다.

## 7. 검증 계약

### 자동 검증

- 각 레코드의 스키마·enum·참조 무결성
- GuardSpec 해시 도메인이 의미 5필드로 한정됨 (같은 내용 → 같은 해시, 시각·id 무관)
- GuardSpec 해시와 사건 참조 일치
- `operation` 사건의 GuardSpec 선행 존재 (append 순서 근거 포함)
- 세션 test 플래그가 켜진 사건이 `operation`으로 저장되지 않음
- 플래그 부재 시 `operation` + `default_inherited` 기록
- 미등록 발동의 `unregistered` 기록과 지표 제외
- 시험/unknown/unregistered 사건이 운영 지표에 들어가지 않음
- 보류값·미처리 제외와 원수 계산, 분자⊆분모
- 두 판단 축의 네 방향 조합
- append·락·부분 쓰기 복구
- 적재 시점 비밀 제거와 정상 양성 대조
- 테스트의 실제 저장소 비접촉
- 비블로킹 실패와 LossRecord·대체 매체 흔적
- 수정 레코드가 원본을 덮지 않음, `test` 강등 amendment 경로
- 판정기 교정 레코드 생성과 미교정 판정의 병기
- drift 감지와 `post-remove` 표시

### 기술 E2E

명시적 시험 가드와 시험 세션으로 전체 흐름을 실행한다. 결과에는 `test evidence only`를 표시하고 사용자 가치 완료라고 부르지 않는다.

### 운영 검증

관찰 시작 전에 — 관측 대상 가드 배선(T3)이 켜지기 전에 — 종료 조건, 평가 질문, 응답 양식, 기준선 측정 절차를 기록해 고정한다. 자연 사건을 기다리며 강제 발동으로 채우지 않는다. 관찰 종료 뒤 기술 상태(완료/미완)와 가치 상태(검증/미검증/가치 실패/채택 실패)를 각각 선언한다.

## 9. 반증과 주장 제한

- 자연 운영 사건 부족은 기술 실패가 아니라 빈도 가설 미검증이다.
- 기록·판정이 의사결정 시간·근거 복원 노력·결정 확신을 개선하지 못하면 해법 가치 가설 실패다.
- 검토 부담이 가치보다 크면 채택 가설 실패다.
- `insufficient_context`가 지배적이면 캡처 설계 실패이며, 캡처 계약을 재설계한다.
- 외부 사용자 실제 사용 전 다른 개발자·팀·시장으로 일반화하지 않는다.
- v1의 최대 주장은 “내 저장소에서 사라지던 가드 발동을 증거 기반 가드 결정으로 바꾸는 개인 도구 실험”이다.
