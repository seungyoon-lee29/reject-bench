# 거부 출력 형식 표준 + 감지·후보 규칙 + 보조 기록 스키마 (v1)

> **선커밋 문서.** spec 3.3이 요구하는 형식 요건·감지 규칙·후보 규칙과, spec 3.5가 요구하는 보조 기록 7종의 스키마를 여기 먼저 고정한다. 생산 태스크(T2 기록기·T3 어댑터/스캐너·T6 생성기)는 이 문서를 따르며, 자기 형식을 스스로 정하지 않는다 — 소유권이 뒤집히면 스키마가 산출물에 맞춰 사후 조정된다.
>
> 행동의 정본은 `.dryforge/spec.md`다. 이 문서와 충돌하면 spec이 이긴다.

## 0. 규칙 버전과 개정

**규칙 버전 = 아래 경로를 마지막으로 건드린 커밋 해시**다. 거부 레코드와 판정 레코드가 이 해시를 참조한다(spec 3.1).

```
docs/형식-표준.md
rejectbench/rules.py
```

조회는 읽기 전용 git이다(`git log -1 --format=%H -- <경로들>`). 불변식 7의 "임의 코드 실행 금지"에 걸리지 않는다.

**개정 규칙**

1. 개정은 커밋으로만. 커밋 사유에 **포착 범위가 넓어졌는지 좁아졌는지를 명시**한다. 좁히는 개정(보수화)은 분모를 줄이는 방향이라 게이밍 채널이 될 수 있고, 그 가시화 장치가 이 표기와 집계의 "규칙 버전별 거부 건수 분포"다.
2. 기준·규칙 개정은 **런북 ⑥ 이후에만** 한다(spec §0 — 발생과 앵커 사이의 개정 창을 좁힌다).
3. 형식의 하위호환은 **버전 번호로만** 보장한다. v1 파서는 `REJECT-BENCH/1`만 구조화하고, 다른 버전은 비정형으로 떨어뜨린다.

## 1. 거부 출력 형식 v1

### 1.1 형태

가드는 **한 줄**을 표준 출력 또는 표준 오류에 낸다.

```
REJECT-BENCH/1 {"guard":"evaluation-live-waste","reason":"거부: `evaluation-live-waste` 은 라이브 실측 리포트 이름인데 …"}
```

- `REJECT-BENCH/<버전>` 표지 뒤에 공백 하나 이상, 그 뒤에 **JSON 객체 하나**.
- **1줄 = 1사건**(spec 3.3). 사건이 둘이면 줄이 둘이다.
- 줄 앞의 공백·탭은 허용한다(래퍼가 들여쓰는 경우가 있다). 줄 뒤 공백도 허용한다.
- 인코딩은 UTF-8. JSON 안에 개행이 필요하면 `\n`으로 이스케이프한다 — 형식이 줄 단위이기 때문이다.

**사람이 읽을 메시지는 이 줄과 별개로 그대로 낸다.** 실물 가드는 한국어 산문으로 사유를 설명하고 비정상 종료한다(예: `거부: \`evaluation-live-waste\` 은 …`). 그 출력을 대체하지 말고, 기계용 한 줄을 **추가로** 낸다. 형식이 사람 출력을 삼키면 가드를 심는 비용이 올라가고, 비용이 오르면 가드가 안 심긴다.

### 1.2 필드

| 키 | 필수 | 타입 | 계약 |
|---|---|---|---|
| `guard` | ✅ | string | 가드 식별자. `^[a-z0-9]([a-z0-9.-]*[a-z0-9])?$`, 1~64자. 등록부 연결 키(spec 3.2) — **재사용 금지** |
| `reason` | ✅ | string | 거부 사유 전문. **절단 금지.** 공백만 있으면 위반 |
| `project` | | string | 1~128자. 없으면 기록기가 읽기 전용 git 조회로 정규화하거나 명시 결측 처리(spec 3.1) |
| `action` | | object | 시도된 행동의 뼈대. 아래 1.3 |
| `occurred_at` | | string | RFC 3339 UTC(`…Z`). 없으면 기록기가 적재 시각을 쓰고 시각 출처를 표시한다 |

**미지정 키는 위반이다.** 새 필드를 넣으려면 형식 버전을 올린다. 느슨하게 열어두면 가드가 임의 키로 판정 쪽에 신호를 흘릴 수 있고, 판정 입력의 텍스트는 이미 피판정자가 쓴 것이라 채널을 더 늘릴 이유가 없다(spec 3.2 방어 지시).

### 1.3 `action` 객체

| 키 | 타입 | 계약 |
|---|---|---|
| `tool` | string | 도구명. 공백 불가 |
| `paths` | string[] | 경로 목록 |
| `argv_heads` | string[] | **복합 명령 구간별 첫 토큰**. 각 원소에 공백 불가 — 공백이 있으면 첫 토큰이 아니라 명령 전문이므로 위반 |

셋 다 선택이고, `action`이 있으면 최소 한 키는 있어야 한다.

**금지**: 파일 내용·인자 전문·프롬프트(spec 3.1). `argv_heads`의 공백 금지는 이 금지를 기계가 확인할 수 있는 유일한 지점이다. `reason`과 `paths`에 무엇이 들어가는지는 형식이 검사하지 못한다 — 가드 작성자 몫이고, 마스킹은 적재 시점에 별도로 걸린다.

### 1.4 예시

준수:

```
REJECT-BENCH/1 {"guard":"evaluation-live-waste","reason":"라이브 실측 리포트 이름인데 이 실행은 실측이 아니다. 다른 --report-stem 을 쓰라.","project":"reply-gate","action":{"tool":"Bash","argv_heads":["uv"]}}
```

위반(→ 비정형 원시 보존, 식별자 복원 시도):

```
REJECT-BENCH/1 {"guard":"evaluation-live-waste"}                  # reason 없음
REJECT-BENCH/1 {"guard":"Eval Live","reason":"…"}                 # 식별자 문법 위반
REJECT-BENCH/1 {"guard":"g","reason":"…","verdict":"맞은 거부"}    # 미지정 키
REJECT-BENCH/2 {"guard":"g","reason":"…"}                         # 미지원 버전
REJECT-BENCH/1 {"guard":"g","reason":                             # JSON 파손
```

## 2. 감지 규칙 v1 — 정형 (어댑터·기록기)

한 줄이 아래를 만족하면 **감지**된 것이다.

```
^[ \t]*REJECT-BENCH/([0-9]+)(?:[ \t]+(.*?))?[ \t]*$
```

- 감지는 **버전도 페이로드도 가리지 않는다.** 표지 뒤가 깨진 JSON이든 빈 문자열이든 감지는 되고, 분류에서 비정형으로 떨어진다. 감지 단계에서 버리면 "형식을 쓰려 했으나 실패한 거부"가 통째로 사라진다 — 그것이 가장 놓치면 안 되는 부류다.
- 표지 뒤에는 공백·탭 또는 줄끝이 와야 한다. `REJECT-BENCH/1garbage`는 감지되지 않는다.
- 감지된 줄은 무조건 기록기로 간다. 파싱 실패는 유실 사유가 아니다(spec 3.3 비정형 백스톱).
- **실행 위치는 자유지만 수집 배선은 로컬 전제다.** CI에서 실행된 가드의 거부는 이번 판에서 수집되지 않는다(spec 3.3 — 가이드·README 경고 대상).

## 3. 후보 규칙 v1 — 비정형 (v0 스캐너)

형식 도입 이전의 거부는 마커 없는 자유문이다. 스캐너는 v0 로그(`data/events.jsonl`)를 읽기 전용으로 훑어 **후보**를 뽑고, 사람이 확인 큐에서 {이관·탈락·중복} 중 하나로 처리한다. 후보 규칙은 판정이 아니라 **사람에게 보여줄 것을 고르는 규칙**이다.

### 3.1 마커

v0 행의 `error` 문자열에 아래 중 하나가 있으면 후보다. **출처 열이 이 표의 핵심이다** — 규칙을 가드 코드에서 뽑았는지, 로그를 보고 뽑았는지를 구분한다. 로그를 보고 만든 규칙은 데이터에 맞춘 규칙이므로 선등록이 아니다.

| # | 마커 | 출처 | 비고 |
|---|---|---|---|
| M1 | `거부:` | 가드 코드 (reply-gate `6e585f9`) | 398행 계열 |
| M2 | `는 지금 돌릴 수 없다` | 가드 코드 (reply-gate `7efc966`) | 628행 계열 |
| M3 | `은 지금 돌릴 수 없다` | 가드 코드 (같은 계열 조사 변형) | `--stub-llm` 자매 가드 |
| M4 | `가드: 거부` | **로그 관찰 (post-hoc)** | 2026-08-12 세션에서 사람이 v0 로그를 훑다 발견. 데이터를 보고 만든 규칙 |
| M5 | `REJECT-BENCH/` | 형식 정의 | 정형 출력이 어댑터를 못 거치고 v0로 샌 경우 |

M4는 **선등록된 규칙이 아니다.** 이 사실은 지우지 않는다 — 규칙이 데이터에서 왔다는 것을 표기해두지 않으면, 나중에 이 규칙으로 잡힌 건수가 "선등록 규칙의 성과"로 읽힌다.

### 3.2 배제 4종 (spec 3.3)

| 코드 | 배제 대상 | 판별 |
|---|---|---|
| (a) | 자기 참조 오염 | 이 저장소에서 유래한 행 — `cwd`/경로가 reject-bench이거나, `error`에 이 저장소의 테스트·문서 경로가 있는 경우 |
| (b) | 기기록 v0 행 | 이미 이관된 행(행 번호 기준) |
| (c) | 기탈락 후보 | 탈락 기록에 있는 행 |
| (d) | 기록 사건 매칭 행 | 정형 경로로 이미 기록된 사건과 같은 사건인 행. **불확실하면 배제하지 말고 큐로 보내 `중복`으로 처리한다** |

(a)는 실제로 발생한다. 이 문서와 파서 테스트가 마커 문자열을 그대로 담고 있어서, 이 저장소에서 테스트를 돌리는 것만으로 후보가 만들어진다.

### 3.3 불완전 마지막 행

v0 로그는 훅이 append하는 중일 수 있다. **마지막 개행 뒤의 조각은 스킵하고 다음 주기에 다시 본다**(spec 3.3). 스킵은 유실이 아니므로 유실 기록 대상이 아니다.

### 3.4 재현율 한계 (명시)

**형식 도입 이전 거부에 대해 이 규칙은 재현율을 보장하지 않는다.** 근거는 실물이다 — 628행 거부는 `` `--live` 는 지금 돌릴 수 없다: `` 로 시작해 `거부:` 접두가 아예 없다. 두 실물 거부가 서로 다른 문장 형태를 썼다는 것은, 안정적인 마커가 애초에 없었다는 뜻이다. 마커 집합을 아무리 늘려도 못 잡는 거부가 남는다.

그리고 v0 경유분은 **200자 절단과 24자 이상 토큰 마스킹을 상속한다.** 절단은 실물 2건에서 확인됐고, 마스킹은 그 2건에서는 발동하지 않았다(`<redacted>` 0개). 어댑터를 먼저 설치하는 것이 이 상속을 피하는 유일한 길이다(가이드 경고 대상).

## 4. 파서 계약

파서는 텍스트 덩어리를 받아 감지된 줄마다 결과 하나를 낸다. 판정도 마스킹도 하지 않는다.

| 분류 | 조건 | 산출 |
|---|---|---|
| `형식 준수` | 감지 + 지원 버전 + JSON 유효 + 필수 필드·타입·문법 전부 통과 | 구조화 필드 |
| `비정형(원시 보존)` | 감지됐으나 위 중 하나라도 실패 | **원시 줄 전문** + 위반 사유 + 식별자 복원 시도 결과 |

- 원시 보존은 줄 전문을 그대로 둔다. 파서가 고쳐 쓰지 않는다.
- **식별자 복원 시도**: JSON이 깨졌어도 `"guard"` 값이 문자열로 읽히면 후보로 삼고, 1.2의 문법을 통과할 때만 복원 성공으로 표시한다. 복원값은 **참고**이며, 판정 가능 여부는 등록부 등재로 결정된다(spec 3.2) — 복원 실패는 "판정 불가(미상)"로 병기된다.
- 위반 사유는 집계에 쓰이므로 코드 문자열로 고정한다: `unsupported_version` · `bad_json` · `not_object` · `missing_field` · `bad_type` · `bad_guard_id` · `unknown_key` · `empty_reason` · `bad_action`.

## 5. 보조 기록 스키마 (7종)

전부 **git 추적 JSONL, append 전용, 기존 줄 불변**이다(spec 불변식 8). 모든 줄은 `schema`(정수)와 `recorded_at`(RFC 3339 UTC)을 갖는다. 원문 인용은 금지다 — 참조 대상(v0 행)이 비공개라 인용하면 비공개 내용이 추적 경로로 새어 나온다.

경로는 `records/` 아래로 모은다.

| # | 산출물 | 경로 | 소유(생산) |
|---|---|---|---|
| 1 | 큐 상태 요약 | `records/큐-요약.json` | T3 |
| 2 | 탈락 기록 | `records/탈락.jsonl` | T3 |
| 3 | 중복 기록 | `records/중복.jsonl` | T3 |
| 4 | 유실 기록 | `records/유실.jsonl` | T6 ⓪ (흔적 → 집계) |
| 5 | 제외 기록 | `records/제외.jsonl` | T6 (생성기 제외 모드) |
| 6 | 정리/정정 기록 | `records/정리-정정.jsonl` | 런북 사고 대응 |
| 7 | 검사 리포트 | `records/검사-리포트.jsonl` | T4 순서 검사 |

### 5.1 큐 상태 요약 (단일 JSON 객체 — 갱신형)

큐 본체는 `data/` 비추적이고, 추적되는 것은 요약뿐이다.

```json
{
  "schema": 1,
  "recorded_at": "2026-08-27T05:00:00Z",
  "pending": 0,
  "oldest_pending_days": null,
  "oldest_pending_since": null,
  "rules_version": "<커밋 해시>"
}
```

`pending`이 0이면 `oldest_*`는 `null`이다. 7종 중 이것만 갱신형(덮어쓰기)인 이유는 "현재 대기 건수"가 이력이 아니라 상태이기 때문이다 — 변화 이력은 git이 가진다.

### 5.2 탈락 기록 (JSONL)

```json
{"schema":1,"recorded_at":"…Z","source":"v0","line":413,"decision":"탈락","rules_version":"…","note":"조회성 명령의 exit≠0 — 거부가 아니다"}
```

- `line`: v0 로그 행 번호(1-based). 행 번호가 참조의 전부다 — **원문 인용 금지**.
- `note`: 한 줄 사유. 필수.

### 5.3 중복 기록 (JSONL)

탈락과 같은 필드에 연결 대상이 붙는다.

```json
{"schema":1,"recorded_at":"…Z","source":"v0","line":631,"decision":"중복","linked_record_id":"…","rules_version":"…","note":"398행으로 이미 이관된 사건과 동일"}
```

`linked_record_id` 필수. 탈락과 중복이 같은 기록 요건을 지는 이유는, 둘 다 분모를 줄이는 결정이고 한쪽만 기록되면 그쪽으로 몰 수 있기 때문이다(spec 3.3).

> **한계(고지)**: 참조 대상인 v0 행이 비공개라 탈락·중복 사유의 내용은 제3자가 검증할 수 없다. 이 기록을 "대칭 장치"로 과대 표현하지 않는다.

### 5.4 유실 기록 (JSONL)

기록기는 비블로킹이라 적재에 실패해도 호출자를 막지 않는다. 대신 흔적을 남기고, 런북 ①이 그 흔적을 세어 여기 옮긴다.

```json
{"schema":1,"recorded_at":"…Z","occurred_at":"…Z","kind":"write_failed","path_hint":"data/events.jsonl","count":1}
```

**원문 금지** — 시각·유형·경로만이다(spec 3.4). `kind`: `write_failed` · `lock_timeout` · `parse_crash` · `unknown`.

### 5.5 제외 기록 (JSONL)

오탐 장면의 공개는 기본값이고, 빼려면 사용자가 명시 지정해야 한다.

```json
{"schema":1,"recorded_at":"…Z","record_id":"…","scope":"장면","reason":"고객사 식별 가능","incident_applied":false,"incident_note":"원장 레코드에는 민감정보 없음 — 사고 대응 미발동"}
```

- `scope`: `장면`(공개 선별에서만 제외).
- `incident_applied`·`incident_note` **필수**: 장면에서 뺄 때 그 원장 레코드에 사고 대응이 필요한지 함께 판단하고 남긴다. **장면만 빼기 금지**(spec 3.5).
- `reason`은 구체적이어야 한다 — "부적절"처럼 내용 없는 사유는 요건 미달이다.

### 5.6 정리/정정 기록 (JSONL)

사고 대응(비밀·PII·사용자 지정 민감정보)의 흔적이다.

```json
{"schema":1,"recorded_at":"…Z","phase":"push_전","action":"이력_정리","record_id":"…","reissued_as":"…","scope":"원장 1줄 + 원본 1줄 + 백업","rotation_advised":true,"note":"마스킹이 놓친 자격증명"}
```

- `phase`: `push_전` · `push_후`.
- `action`: `이력_정리`(push 전 기본) · `tombstone`(push 후) · `재발행` · `이력_재작성`(심각 유출 — force-push 예외).
- `reissued_as`: 재발행 레코드 id. 재발행은 **원 id·원 앵커 참조를 승계**하므로 조상 검사는 최초 앵커 기준으로 계속 성립한다(spec §0).
- push 전에는 tombstone을 쓰지 않는다 — 평문이 공개 이력에 실린다.

### 5.7 검사 리포트 (JSONL)

선커밋 순서(조상 관계) 검사의 결과다.

```json
{"schema":1,"recorded_at":"…Z","verdict_id":"…","record_id":"…","verdict_type":"독립 첫 판정",
 "precommit_shas":{"기준":"…","프롬프트":"…","실행설정":"…","규칙":"…"},
 "anchor_sha":"…","verdict_sha":"…",
 "ancestry_ok":true,"anchor_pushed_before_verdict":false,
 "substantive":false,"exempt":false,"skipped":null,"note":"remote 없음 — 실질 보증 미계상"}
```

- `anchor_sha`는 **최초 앵커**다. 재발행·tombstone 줄의 커밋이 아니다.
- `ancestry_ok`: `선커밋 ⊂ 최초 앵커 ⊂ 판정` 조상 관계. **커밋 시각 비교 금지**(불변식 4).
- `exempt`: 재판정은 정의상 기준이 앵커보다 늦으므로 검사 면제 + 병기 대상이다.
- `substantive`: 실질 보증 계상 여부. 출처가 소급이 아니고, 유형이 독립 첫 판정이고, 조상 관계가 성립하고, **판정 시점 이전에 앵커가 push돼 있었을 때만** 참이다.
- `skipped`: shallow 클론·zip 배포라 전체 이력이 없으면 검사를 건너뛰고 그 사실을 여기 남긴다(`"shallow"`).

> `anchor_pushed_before_verdict`는 **자기 보고**다. 무엇이 언제 push됐는지를 제3자가 사후 식별할 수단은 없다(spec 3.7-4).

## 6. 이 문서가 보장하지 않는 것

- 형식은 `reason`·`paths`에 파일 내용이나 프롬프트가 들어가는 것을 막지 못한다. 기계가 볼 수 있는 것은 `argv_heads`의 공백 여부뿐이다.
- 후보 규칙은 형식 도입 이전 거부에 대해 재현율을 보장하지 않는다(3.4).
- 보조 기록은 결정을 남기게 할 뿐, 그 결정이 옳은지는 검증하지 않는다. 탈락·중복 사유의 내용은 제3자 검증 불가다(5.3).
