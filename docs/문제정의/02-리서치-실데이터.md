# 문제정의 2단계 — 리서치 (a) 실데이터

분석 일자 2026-08-10. 대상 `data/events.jsonl`, 수집 2026-08-04T08:14 ~ 2026-08-10T06:0x (약 6일).
**스냅샷 1,022건** 기준. 분석 도중에도 이 세션의 편집이 계속 적재돼 1,012 → 1,022로 늘었다(수집기가 살아 있다는 방증이자, 향후 집계는 스냅샷 시각을 고정해야 한다는 뜻).

목적: 방법론 2단계에서 요구하는 "객관적 지표". 인터뷰(`01`)에서 나온 가설 — **"현재 수집기로 기각을 포착할 수 없다"** — 을 데이터로 확정하거나 기각한다.

## 요약 (먼저)

수집기 v0는 **6일간 정상 작동했고, 목표한 신호는 하나도 잡지 못했다.** 스키마 결함 5개가 확인됐으며, 그중 3개는 문서에 적힌 가정이 데이터와 정면으로 어긋나는 경우다. 동시에 **의도하지 않은 곳에서 진짜 기각 사례 2건이 발견**됐다 — 이게 v1 설계의 실마리다.

## 1. 이벤트 분포

| 이벤트 | 건수 | 비율 |
|---|---|---|
| `PostToolUse` (적용=승인) | 948 | 92.8% |
| `PermissionRequest` (분모) | 39 | 3.8% |
| `PostToolUseFailure` | 33 | 3.2% |
| **`PermissionDenied` (핵심 신호)** | **2** | **0.2%** |

기각 2건은 **둘 다 `tool: Bash`, `cmd: cd`** (08-04T08:14:59, 08-04T18:16:26). 즉 6일간 **Edit/Write/MultiEdit 제안이 기각된 사례는 0건**이다.

## 2. 결함 ①: 분모가 분모가 아니다 — `PermissionRequest`의 85%가 `AskUserQuestion`

| tool | 건수 | 비율 |
|---|---|---|
| `AskUserQuestion` | 33 | 85% |
| `WebFetch` | 2 | 5% |
| `Bash` | 2 | 5% |
| `Skill` | 1 | 3% |
| `WebSearch` | 1 | 3% |

`AskUserQuestion`은 **AI가 사용자에게 질문을 띄운 것**이지 코드 변경 승인을 요청한 것이 아니다. `Edit`/`Write`에 대한 `PermissionRequest`는 **0건**이다.

→ `README.md`가 `PermissionRequest`를 "승인 요청 발생(분모 계산용)"으로 규정한 것은 **틀렸다.** 이 분모로 기각률을 계산하면 "AI가 나에게 질문한 횟수 중 Bash `cd`가 거부된 비율"이라는 무의미한 수가 나온다. `기획-입력.md` 성공 지표 첫 줄("AI 제안 N건 중 기각률 X%")은 현재 스키마로 **계산 불가**다.

## 3. 결함 ②: `PostToolUseFailure`의 3분의 2가 실패가 아니다

33건 중 **22건(67%)** 이 `ls`·`grep`·`wc`·`cat`·`head`·`which`·`sed`·`git`·`cd`·`for` 등 **조회성 명령의 exit≠0**이다. 실제 내용은 정상 출력인데 exit code만 0이 아닌 경우가 대부분이다.

```
08-10T05:32:38  cmd=ls    err: total 0 / drwxr-xr-x@ 2 ian staff 64 ...   ← 정상 출력
08-10T05:19:23  cmd=grep  err: 434:### LangGraph 가 유리했을 지점 ...      ← 정상 검색 결과
08-10T07:07:09  cmd=grep  err: (eval):1: no matches found: --include=*.py  ← zsh 글롭 실패
```

실행성 명령의 실패는 `uv` 4 · `python3` 4 · `timeout` 1 · `pip` 1 · `StructuredOutput` 1 = **11건**뿐이다.

→ `README.md`가 `PostToolUseFailure`를 "테스트 미통과 등 간접 기각 신호"로 규정한 것은 **신호 대 잡음비 1:2**다. 그대로 집계하면 "기각 사유: 테스트 미통과"가 셸 조회 실패로 부풀려진다.

## 4. 결함 ③: 재작업과 정상 진행을 구분할 수 없다

같은 세션·같은 파일의 연속 편집 간격(재편집 쌍 695건, 전체 편집의 73%):

| 지표 | 값 |
|---|---|
| p25 | 6초 |
| **중앙값** | **12초** |
| p75 | 45초 |
| p90 | 1,470초 |
| 30초 이내 | 495건 (71%) |
| 300초 이내 | 582건 (84%) |

중앙값 12초는 **사람이 판단하고 되돌린 간격이 아니라 AI가 한 논리적 변경을 여러 `Edit` 호출로 쪼갠 간격**이다. 즉 "같은 파일 반복 편집 = 재작업"이라는 대리 지표는 성립하지 않는다.

구분할 방법도 없다. **`Edit` 이벤트에 기록되는 필드는 `event`·`path`·`project`·`schema`·`session_id`·`tool`·`ts` 7개뿐**이고, `size`는 `Write`(149건)에만 채워진다 — `Edit` 799건 중 `size` 보유 **0건**. 변경 규모도, 같은 줄을 다시 건드렸는지도 알 수 없다.

참고로 "실패 후 10분 내 같은 세션에서 편집이 뒤따른" 연쇄는 33건 중 **20건**이다. 이건 살아 있는 신호지만(§7), 위 잡음 문제를 먼저 풀어야 쓸 수 있다.

## 5. 결함 ④: `project` 필드가 프로젝트를 가리키지 않는다

`project`는 `os.path.basename(cwd)`인데, dryforge가 worktree에서 작업하므로 **worktree 이름이 프로젝트로 둔갑**한다.

```
project='T5'            → 실제 경로 ~/workspace/reply-gate/.dryforge/worktrees/T5/src/...
project='.dryforge'     → 실제 경로 ~/workspace/reply-gate/.dryforge/spec.md
project='포지션찾기'      → 실제 경로 ~/workspace/reject-bench/기획-입력.md  (7건)
project='reject-bench'  → 실제 경로 ~/.claude/plugins/cache/... (2건), ~/.claude/projects/.../memory/ (2건)
```

즉 **cwd와 편집 대상이 다른 경우를 전부 오분류**한다. 경로로 정규화하면(worktree 접두사 제거) 실제 분포는 이렇다:

| project 필드 기준 | 경로 정규화 기준 |
|---|---|
| reply-gate 905 · T5 57 · 포지션찾기 24 · reject-bench 18 · .dryforge 7 | **reply-gate 857** · reject-bench 14 · 포지션찾기 8 · 기타(홈 밖·`~/.claude` 등) 69 |

→ 대시보드의 프로젝트별 집계를 `project` 필드로 만들면 **틀린 그림**이 나온다. 경로 정규화가 필수다.

## 6. 결함 ⑤: `.dryforge/` 경로 = 상류 기각 대리지표라는 가정이 80% 틀렸다

`HANDOFF.md`와 `기획-입력.md`는 "dryforge 계약서가 `.dryforge/` 아래 Markdown이라 수정 이벤트가 이미 `path`에 잡힌다 → **수집기 변경 불필요**, 사후 집계로 뽑는다"고 적었다. 실측:

| `.dryforge` 포함 편집 | 480건 |
|---|---|
| 계약서 3종(`spec.md`·`plan.md`·`handoff.md`) | **98건 (20%)** |
| `worktrees/` 아래 일반 소스코드 | **382건 (80%)** |

경로 필터 없이 `.dryforge`로 집계하면 **80%가 계약서가 아닌 것으로 오염**된다. "수집기 변경 불필요"는 맞지만 "사후 집계로 뽑는다"에는 정규식 필터가 반드시 붙어야 하고, 그 사실이 어디에도 적혀 있지 않다.

계약서 98건(spec 44 · plan 38 · handoff 16)은 그 자체로는 유효한 상류 신호다. 다만 이것도 "승인 전 수정"인지 "승인 후 갱신"인지 구분할 근거가 로그에 없다.

## 7. 뜻밖의 발견: 진짜 기각이 `error` 필드에 우연히 잡혔다

`PostToolUseFailure`의 마스킹된 에러 메시지 안에, **reply-gate 프로젝트가 자체적으로 걸어둔 가드가 AI의 실행을 거부한 기록**이 있다.

```
08-05T03:23:31  cmd=uv
  거부: `evaluation-live-waste` 은 라이브 실측 리포트 이름인데 이 실행은 실측이 아니다
  (측정 2 미실행 또는 대역). 라이브 산출물을 덮어쓰면 문서가 인용하는 수치의 근거가 …
```
```
08-06T08:12:08  cmd=cd
  `--live` 는 지금 돌릴 수 없다: L2 판정이 켜져 있는데(기본 켜짐) 리포트가 그 사실을
  담지 못한다 — 실행 조건에 L2 켜짐 여부도 판정 모델도 남지 않고, 이름도 사이클 1 실측과 …
```

이것이 이 6일치 로그에서 **의미 있는 "기각"에 가장 가까운 2건**이다. 특징:

- 기각한 주체가 사람도 permission 다이얼로그도 아니라 **프로젝트에 심어둔 가드**다
- 기각 사유가 **자연어로, 도메인 근거와 함께** 남아 있다 (`기획-입력.md`가 원하던 "기각 사유↔근거 매핑"의 원형)
- 그런데 수집기는 이걸 "Bash 실패"로 분류했다. 잡힌 건 **우연**이고, `ERR_MAX=200`자 절단과 24자 이상 토큰 마스킹(`<redacted>`)에 걸려 근거의 뒷부분이 잘려 있다

→ **v1이 잡아야 할 것의 형태가 여기 있다.** "누가 무엇을 왜 거부했는가"가 구조화되지 않은 채 에러 문자열에 섞여 들어왔다.

## 9. 이 문서가 확정한 것

1. **`PermissionDenied` = 기각이라는 등식은 데이터로 기각됐다.** 6일 · Edit/Write 948건 · 기각 0건.
2. **기각률은 현재 스키마로 계산 불가.** 분자도 분모도 무효(§2).
3. **재작업 대리 지표도 현재 스키마로 추출 불가.** 변경 규모·내용이 없어 12초 재편집과 재작업을 구분할 수 없다(§4).
4. **문서에 적힌 가정 3개가 사실과 다르다** — `README.md`의 `PermissionRequest` 분모 규정, `PostToolUseFailure` 간접 신호 규정, `HANDOFF.md`/`기획-입력.md`의 `.dryforge` 대리지표 규정. **세 문서 모두 개정 대상.**
5. **`project` 필드는 집계에 쓸 수 없다**(§5). 경로 정규화 필요.
6. **진짜 기각의 형태는 "가드가 자연어 근거와 함께 거부한 것"이었다**(§7). 이게 v1 스키마와 문제정의의 출발점 후보다.

## 10. 이 문서가 남기는 질문 (→ `03-문제후보.md`)

- 기각을 "permission 거부"가 아니라 무엇으로 **조작적으로 정의**할 것인가? 후보: ①가드/훅의 거부 ②실패→수정 연쇄 ③사용자 발화의 부정 신호 ④되돌림(git) — 각각 관측 비용과 신뢰도가 다르다
- v0 로그 6일치는 **버리는가, 재해석하는가?** (원본성 원칙상 재작성 금지. 다만 "무엇을 못 잡았는가"의 증거로서는 가치가 있다 — 실패한 계측 자체가 이 프로젝트의 서사가 될 수 있는지가 담금질 대상)
- 이 계측 실패는 **나만의 문제인가, AI 코딩 도구를 계측하려는 모든 팀의 문제인가?** 후자라면 그게 문제정의다 (→ 외부 리서치와 교차)
