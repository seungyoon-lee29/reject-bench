# I. AI 코드 리뷰 도구

## 1. 가장 중요한 발견 — 아무도 오탐률을 공개하지 않는다

**Greptile 자체 벤치마크** (2025-07, 실제 PR 50건, Sentry·Cal.com·Grafana 등 5개 OSS 저장소)
출처: https://www.greptile.com/benchmarks

| 도구 | 버그 탐지율 | Critical 탐지율 |
|---|---|---|
| Greptile | 82% | 58% |
| Cursor Bugbot | 58% | 58% |
| GitHub Copilot | 54% | 50% |
| CodeRabbit | 44% | 33% |
| Graphite | 6% | 17% |

원문 방법론에 이렇게 적혀 있다:

> "Scoring considered only detection of the original bug; false positives, style suggestions, and unrelated comments did not affect the catch rate."
> (채점은 원래 버그의 탐지만 고려했다. 거짓양성·스타일 제안·무관한 코멘트는 탐지율에 영향을 주지 않았다.)

**즉 업계 대표 벤치마크가 오탐을 의도적으로 채점에서 제외한다.** 여러 3차 블로그가 인용하는 "Greptile 11 FP vs CodeRabbit 2 FP"라는 수치는 **Greptile 공식 페이지에 존재하지 않는다** — 1차 출처 확인 실패.

## 3. 학술 근거

### "Are LLMs Reliable Code Reviewers? Systematic Overcorrection in Requirement Conformance Judgement"
Haolin Jin, Huaming Chen · arXiv:2603.00539v1 (2026-03-03, CC-BY 4.0) · https://arxiv.org/pdf/2603.00539

핵심: **"systematic overcorrection"** — LLM이 요구사항을 **이미 충족한 정상 코드**에 대해서도 높은 비율로 문제가 있다고 오탐하는 구조적 결함. (상세 precision 수치는 논문 Table 11/13/22. 본 조사에서는 메타데이터 수준까지만 확인 — 원문 재확인 권장)

### "Go Home Copilot, You're Drunk: Understanding Developer Responses to Agent-Generated Code Review Comments"
Cynthia·Widyasari·Roy·Zhang·Lo (Saskatchewan / SMU / Monash) · arXiv:2607.21997v1 (2026-07-24) · https://arxiv.org/html/2607.21997v1

방법: Copilot·Cursor·Codex 3종, **Python 저장소 342개 · 코멘트 54,713건** 분석, 15개 카테고리 분류(Cohen's κ=0.74).

| 에이전트 | 코멘트 해결율 |
|---|---|
| GitHub Copilot | **72.9%** |
| Cursor | 67.2% |
| OpenAI Codex | 54.8% |

- 코어 개발자(상위 20% 기여자)는 Copilot 코멘트의 **78.1%** 해결 — 주변부 기여자보다 훨씬 높음
- **인라인 코드 제안이 포함된 코멘트 75.5% 해결 vs 제안 없는 코멘트 64.6%**
- 미해결 코멘트 15,652건 중 답글이 달린 것은 1,056건뿐
- 미해결 사유 오픈 카드소팅(470건): 1위 **"Intentional Design Decision"(의도적 설계 결정, 112건)**, 2위 **"Incorrect Suggestion"(잘못된 제안=오탐, 67건)**

→ **미해결의 최다 사유가 "오탐"이 아니라 "의도적 설계 결정"이라는 점이 중요하다.** 리뷰어가 무시하는 코멘트의 상당수는 틀려서가 아니라 **도구가 모르는 맥락 때문**이다. 이건 "정적 분석 + LLM 조합"으로 풀리는 문제가 아니다.

### 미확인
arXiv:2601.00753 "Early-Stage Prediction of Review Effort in AI-Generated Pull Requests" — 검색 스니펫에 *"nearly 70% of agent-authored PRs face longer review times, remain completely unreviewed, or get rejected soon"* 라는 문구가 있었으나 **원문 fetch 실패(세션 한도)**. 확인 실패.

## 6. 설문 기관 데이터

### DORA 2025 — "verification tax"
https://dora.dev/insights/balancing-ai-tensions/ · 원 리포트: cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report

- **개발자 30%가 "AI 생성 코드를 거의/전혀 신뢰하지 않는다"**
- 핵심 개념 **"verification tax"**: *"the time saved during initial code or content generation is often re-allocated to verification overhead"* (초기 코드 생성에서 아낀 시간이 결국 검증 오버헤드로 재배치된다)
- 개발자 인용: *"Reviewing [another's] code is so much harder than writing it. AI tools are increasing the rate at which people can churn out code that needs to be reviewed…"*
- 개발자 인용: *"I feel somewhat more productive, but it's at a cost. While I end up spending less time writing code, I spend more time babysitting the AI and reviewing what it is trying to do."*
- 60% 이상이 배포 후 AI 관련 오류를 발견한 경험 (원문 대조 권장)
- 역설: 기술직 90%가 AI 사용, 80%+가 생산성 향상 체감 — 그럼에도 검증 부담은 남는다

### Stack Overflow 2025 개발자 설문 (원문 직접 확인)
https://stackoverflow.blog/2025/12/29/developers-remain-willing-but-reluctant-to-use-ai-the-2025-developer-survey-results-are-here/ (2025-12-29)

https://github.com/fn-opt/dryforge · MIT · 2026-08-10 API 관측

- **Star 122 / Fork 14 / Open issues 0**. 생성 2026-05-31, 최근 push 2026-07-19(README 편집)
- 저자 `fn-opt`의 공개 저장소는 dryforge 하나뿐 — **1인 개인 프로젝트**로 보임. 조직 배경 확인 실패
- 릴리스: v0.1(05-31) → v1.0.0(06-07) → v1.1.0(06-09) → v1.1.1(06-12, 06-27 재커밋) → 이후 **약 3주 신규 커밋 없음**
- 자기 규정: "planner+orchestrator+memory 번들"이 아니라 **"bounded-autonomy 플러그인 하네스"**. 권한(authority)을 6계층(user/specification/plan/code/evidence/project harness)으로 분리하는 것이 핵심 주장

**3개 진입점**: `ready`(입력 → 실행 가능한 계약) · `go`(승인된 계약 실행) · `migration`(기존 코드베이스에 프로젝트 컨텍스트 수립)

**계약서 = `.dryforge/` 아래 순수 Markdown 3종**: `spec.md`(권위 있는 동작·제약·불변식·엣지케이스·검증 항목) · `plan.md`(작업별 행동 계약, 의존성 그래프 YAML — `depends`/`regen_barriers`/`risk: RISKY|MECHANICAL|NONE`) · `handoff.md`(문서 간 권위 관계, 재추론 금지 의도)

**게이트 구조** (`ready/SKILL.md` 27,799자 직접 확인):
1. **intent-completeness** — 대화 전체를 근거로, 스펙 작성자가 인지하지 못한 채 채워 넣은 "guess"(비근거 가정)를 사냥
2. **3-doc-gate** — **대화를 못 본 fresh subagent**가 완성된 3-doc만 보고 실행가능성을 감사. "최종 백스톱"이며 "찾는 게 없어야 정상"
3. **USER GATE** — 유일한 인간 체크포인트("Review this and confirm")

`go`는 코드 생성 후 게이트로, *"완료는 자신감 진술이 아니라 증거 주장(evidence claim)"*이라 규정하고 검증 깊이를 리스크에 비례 조정.

### 명시적으로 하지 않는 것 — **여기가 핵심**

저장소 전체 코드 검색 `telemetry OR metrics OR analytics OR measure` → **0건**.

- **텔레메트리·메트릭·분석 없음.** README에 "성공률", "리젝률 감소" 같은 측정치나 대시보드 언급 전무
- **승인/거부 결정을 데이터화하지 않음.** USER GATE는 대화 중 1회성 승인이고, 완료된 계약은 `.dryforge`에 로컬 Markdown 아카이브로만 남는다
- **"계약 단계가 실제로 다운스트림 기각을 줄였는지" 측정할 어떤 구조도 없다**

→ dryforge는 **워크플로/프롬프트 하네스**이지 데이터 수집 시스템이 아니다. 내 프로젝트와 **기능이 겹치지 않는다**는 것이 코드 수준에서 확인됐다.

## 10. 결정적 반증 — spec-driven이 오히려 rework를 늘렸다는 대규모 실증

> **Brenn Hill, "Does Spec-Driven Development Reduce Defects? An Empirical Test of Industry Claims Across 119 Open-Source Repositories"**, SSRN, 2026-04
> https://papers.ssrn.com/sol3/papers.cfm?abstract_id=6515898

방법: GitHub Spec Kit·Amazon Kiro 등 **벤더 주장 5개 가설**을 SZZ 결함 추적 + **author 내 고정효과(within-author fixed-effects)** 로 검증. **PR 100,247건 / 오픈소스 저장소 119개.**

결과:
- **5개 가설 중 어느 것도 지지되지 않았다**
- author-내 비교에서 스펙 사용은 **결함률 +1.4%p (p=0.056)**, **rework +5.0%p (p<0.001, 통계적으로 유의)** 증가와 연관
- **스펙 품질(quality)은 rework에 영향 없음(zero effect)**
- 결론: *"스펙 아티팩트는 품질 개선이 아니라 **태스크 복잡도의 대리지표(proxy)**로 기능한다"*

> ⚠️ **주의**: SSRN 원문이 Cloudflare Turnstile(HTTP 403)로 차단돼 **본문 직접 열람 실패**. 위 수치는 검색엔진 색인 초록·2차 인용 기반이다. 저자 소속과 정확한 게재일 확인 실패. **인용 전 원문 대조 필수.**

이 논문은 dryforge·Kiro·Spec Kit이 공통으로 내세우는 *"스펙을 먼저 쓰면 재작업이 준다"*는 핵심 전제에 대한 **최초의 대규모 독립 반증**으로 보인다. **어떤 벤더도 공개 반박 데이터를 제시하지 않았다**(확인 범위 내).

대조군: Deepak Babu Piskala의 arXiv 프리프린트(arXiv:2602.00180v1, 2026-01-30)는 "오류 최대 50% 감소", "통합 사이클 타임 75% 감소"를 인용하지만 **본인의 1차 연구가 아니라 타 연구 재인용**이고, 동시에 spec rot·over-specification·false confidence(스펙 테스트 통과 ≠ 정확성) 한계를 명시한다.

## 12. spec-driven에 대한 공개 비판

**Martin Fowler, "Understanding Spec-Driven Development: Kiro, spec-kit, and Tessl"** (2025-10-15, 원문 직접 확인)
https://www.martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html

Kiro/spec-kit/Tessl을 spec-first / spec-anchored / spec-as-source 3단계로 분류한 뒤 5가지 비판:
1. 작은 버그와 큰 기능이 **동일하게 무거운 워크플로**를 강제받는 워크플로 불일치
2. 방대한 Markdown 산출물의 **리뷰 부담** (코드와 중복되어 지루함)
3. 상세 스펙에도 불구하고 에이전트가 지시를 무시·과잉해석하는 **실행 갭**
4. spec-as-source가 과거 실패한 **Model-Driven Development의 재현**이 될 위험 (LLM 비결정성 + MDD 경직성의 결합)
5. **"spec-driven development"라는 용어 자체의 개념적 모호성** — 정교한 프롬프트와의 구분 불명확

**Thoughtworks (Liu Shangqi, Technology Director APAC)**:
> "Spec drift and hallucination are inherently difficult to avoid. We still need highly deterministic CI/CD practices to ensure software quality and safeguard our architectures."

같은 글에서 *"경험 많은 개발자는 과도하게 형식화된 스펙이 불필요한 문제를 일으키고 변경·피드백 주기를 늦출 수 있다 — 초기 waterfall 시절과 마찬가지로"*라고 명시. (게시일 원문 미표기 — 확인 실패)

**확인 실패**: Kent Beck의 비판, Brandon Kindred "Same Patterns, New Hype"(2026), ThoughtWorks Technology Radar Vol.33(2025, SDD를 "Assess" 링에 배치)은 검색 요약에만 등장하고 **1차 출처를 열지 못했다**(세션 한도). 인용 전 원문 대조 필요.

## 빈 자리(gap) 후보

1. **오탐률을 정직하게 공개하는 주체가 없다.** 업계 대표 벤치마크(Greptile)가 FP를 채점에서 명시적으로 제외하고, 6개 벤더가 같은 벤치마크로 각자 1등을 주장한다. **"내 검증기의 오탐률을 그대로 공개한다"는 것 자체가 희소하다.** — `기획-입력.md` 확정 사항 7("불리해도 그대로 낸다")이 우연이 아니라 시장의 빈 자리와 정확히 겹친다.

3. **"의도적 설계 결정"으로 무시되는 코멘트가 최다**(arXiv:2607.21997)인데, 이 맥락을 학습·반영하는 도구가 없다. 도구가 모르는 프로젝트 맥락을 어떻게 주입할 것인가는 미해결.
4. **spec-driven의 효과가 대규모 실증에서 반증됐는데**(SSRN, rework +5.0%p) 어떤 벤더도 반박 데이터를 내지 않았다. **측정 자체가 비어 있는 영역.**
5. **AI 코딩 세션의 "거부"를 계측하는 도구가 없다.** (도구 지형 조사 (d) 항목은 세션 한도로 미완 — 별도 확인 필요)
