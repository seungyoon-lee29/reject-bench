# 문제정의 — 계획과 현재 정본 (2026-08-27)

> 이 문서는 `docs/문제정의/` 절차와 완료 기준의 정본이다. 과거 산출물은 번호 순서대로 보존하고, 현재 결론은 가장 뒤의 문서가 맡는다.

## 현재 상태

- 1차 문제정의(01~05)는 2026-08-10~11에 완료됐다.
- 구현 준비와 당시 계획의 T1(폐기된 v6 라벨)을 진행한 뒤, 2026-08-27에 문제정의를 다시 열었다.
- 재검토 결과는 [`06-v7-문제정의.md`](06-v7-문제정의.md)가 정본이다.
- [`05-최종-문제정의.md`](05-최종-문제정의.md)는 당시 판단의 역사 기록이며 현재 계획의 입력으로 사용하지 않는다.
- v7 본체 행동 계약과 순서는 각각 [`.dryforge/001/spec.md`](../../.dryforge/001/spec.md), [`.dryforge/001/plan.md`](../../.dryforge/001/plan.md)가 맡는다. MCP 조회 증분 계약은 [`.dryforge/002/spec.md`](../../.dryforge/002/spec.md)다.
- 사용자가 v7 문서를 승인했고, 기존 준비 구현은 전용 D1 정리 커밋에서 폐기했다.
- 2026-08-28에 적대 리뷰([`../v7-기획-적대리뷰.md`](../v7-기획-적대리뷰.md))와 포트폴리오 인터뷰로 finding 수용을 결정하고 정본에 반영했다. 결정 기록은 [`07-포트폴리오-인터뷰.md`](07-포트폴리오-인터뷰.md)다.

## 사용한 절차

### 1차 사이클 — 탐색과 후보 비교

| 단계 | 행동 | 산출물 |
|---|---|---|
| 1. 인터뷰 | 기존 가정과 실데이터 충돌을 확인 | `01-인터뷰.md` |
| 2. 리서치 | 실데이터·공고·도구·커뮤니티 조사 | `02-리서치-*.md` |
| 3. 후보 심사 | 후보 전량을 두 심사 관점으로 채점 | `03-문제후보.md`, `04-심사결과.md` |
| 4. 담금질 | 반증·최소 성립선·차별점을 조임 | `05-최종-문제정의.md` |

### 2차 사이클 — 구현 후 문제 재개방

1. 이미 구현된 해법에서 출발하지 않고 사용자의 실제 결정 작업을 다시 찾았다.
2. 관찰된 사실과 아직 검증되지 않은 가설을 분리했다.
3. 정책 일치성과 사용자 유용성을 서로 다른 판단으로 분리했다.
4. 시험 발동과 자연 운영 발동을 증거 생성 시점부터 분리했다.
5. 최소 성공을 지표 숫자가 아니라 실제 가드 수명주기 결정 1건으로 다시 정의했다.
6. 새 문제에 맞춰 v7 spec·plan을 백지에서 설계하고, 기존 구현은 승인 뒤 폐기하기로 했다.

### 3차 사이클 — 적대 리뷰와 포트폴리오 인터뷰 (2026-08-28)

1. 동일 지시·상호 비가시 블라인드 리뷰어 2 + 메인 독립 검증으로 v7 기획 전체를 적대 리뷰했다(`../v7-기획-적대리뷰.md`).
2. grill 인터뷰로 관측 대상·작업 순서·출고선·origin 기본값·성공 판정 장치·finding 수용 범위를 확정했다(`07-포트폴리오-인터뷰.md`).
3. 수용분을 06·spec·plan·기획-입력에 반영하고, 기각은 사유와 함께 07에 남겼다.

## 완료 기준

문제정의 재검토는 다음을 모두 명시하면 완료다.

- 누구의 어떤 반복 문제인지, 그리고 이 도구가 필요한 최소 사용 조건
- 관찰된 사실과 미검증 가설
- 현재 대안과 그 한계
- LLM 정책 판정과 사용자 유용성 판단의 역할 경계
- 시험 증거와 운영 증거의 경계
- 최소 성공 흐름, 지표의 분자·분모, pending 처리
- 반증·중단 조건과 주장 범위
- 새 구현 계획과 기존 구현의 처리 원칙

위 항목은 `06-v7-문제정의.md`에 모두 기록됐고 사용자 승인을 받았다. v1 본체의 실행 상태와 frontier는 `.dryforge/001/plan.md`, 현재 세션 상태는 루트 `HANDOFF.md`만 기록한다.

## 공통 원칙

- 실측과 가설을 섞지 않는다. 계획된 기능이나 예시 수치를 관찰 결과로 쓰지 않는다.
- 분모가 0이면 기술 파이프라인 성공과 무관하게 사용자 가치는 미검증이다.
- 시험 발동은 기술 검증에만 쓴다. 운영 가치 지표에 섞지 않는다.
- 자연 운영 사건이 생길 때까지 기다리는 캘린더 시간은 구현 실패가 아니다. 다만 사건이 없으면 빈도 가설은 검증되지 않은 채로 남긴다.
- 리서치·심사 결과와 실패한 계측 원천은 삭제하지 않는다.
- 컨텍스트가 부족해지기 전에 `HANDOFF.md`를 먼저 갱신한다.
