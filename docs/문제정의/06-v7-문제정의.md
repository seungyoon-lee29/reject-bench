# 문제정의 재설계 — v7 정본

작성 2026-08-27. 개정 2026-08-28 — 적대 리뷰([`docs/v7-기획-적대리뷰.md`](../v7-기획-적대리뷰.md)) 수용분과 포트폴리오 인터뷰([`07-포트폴리오-인터뷰.md`](07-포트폴리오-인터뷰.md)) 결정 반영. 입력: 01~05의 조사 기록, 수집기 v0 실측, 폐기된 준비 구현에서 드러난 제약, 사용자와의 재인터뷰 두 차례(2026-08-27 — 소급 기록 없음, 2026-08-28 — 07에 기록).

> 이 문서가 현재 문제정의의 정본이다. 05와 기존 v6 계약은 역사 기록이며, v7 계획의 근거로 사용하지 않는다.

## 1. 문제 한 문장

> **여러 AI 코딩 세션에서 지속형 가드를 운영하는 1인 개발자는, 가드 발동 사건과 당시 맥락이 구조화되어 남지 않아 그 가드가 명시 정책대로 막았는지와 실제로 도움이 됐는지 검증할 수 없고, 결국 기억과 흩어진 오류 로그에 의존해 가드를 유지·수정·제거한다.**

Reject Bench가 돕는 핵심 작업은 **가드별 증거를 바탕으로 그 가드를 유지·수정·제거하는 결정**이다. 범용 코드 리뷰, AI 품질 평가, 팀 생산성 분석이 핵심 작업은 아니다.

## 2. 대상 사용자와 최소 사용 조건

- 1차 사용자: 하나 이상의 저장소에서 여러 AI 코딩 세션에 걸쳐 지속형 가드를 운영하는 1인 개발자. 가드는 저장소 전용일 수도, 전역 훅처럼 여러 저장소에 걸쳐 적용될 수도 있다.
- 지속형 가드: 한 번의 프롬프트가 아니라 여러 세션에 걸쳐 같은 규칙으로 반복 적용되는 차단 장치. 도구 도입 전에는 식별자·버전 없이 훅 스크립트나 설정으로만 존재할 수 있으며, 식별자와 버전은 등록 시점에 부여된다.
- 최소 사용 조건: 동일 가드가 여러 세션에서 운영되고, 자연 발동을 기다릴 의사가 있어야 한다
- 제외: 일회성 프롬프트, 단발성 테스트 규칙, 가드가 전혀 없는 저장소
- v1 한정: 차단형 발동만 다룬다. 경고 후 통과형 발동은 유용성 판단의 의미가 달라 v1 범위 밖이다.

단일 세션의 한 번짜리 거부만으로는 이력 축적이나 수명주기 결정 도구의 필요성을 입증할 수 없다.

### v1 관측 대상

v1은 실존하는 지속형 가드 2개를 관측 대상으로 고정한다(결정 근거: [`docs/adr/0001-관측대상-실존-가드-앵커.md`](../adr/0001-관측대상-실존-가드-앵커.md), 07 인터뷰 Q1·Q2).

- 전역 `~/.claude/hooks/block-dangerous-git.sh` — 위험 git 명령 차단. heredoc 속 문서 텍스트만으로 오차단된 이력 2회가 기록돼 있어 수명주기 결정(modify) 후보가 이미 존재한다.
- reply-gate `.claude/hooks/protect-live-reports.sh` — 커밋된 라이브 실측 리포트의 사후 편집 차단. Claude Code와 Codex 양쪽에 배선돼 있다.

1차 관측 무대는 reply-gate 배포 잔여 작업 세션들이고, 전역 가드가 발동하는 다른 저장소 세션도 관측 범위에 포함한다. 관측 도중 가드를 새로 추가하는 것은 허용하되, 그 가드의 사건은 보고서에 별도 표기한다.

## 3. 현재 확인된 것과 아직 모르는 것

### 관찰된 사실

- 기존 수집기에서 실제 가드 거부와 사유는 구조화 사건이 아니라 일반 오류 문자열에 우연히 섞여 들어왔다.
- 그 문자열은 절단됐고, 거부 당시 어떤 버전의 가드 맥락이 적용됐는지 별도 레코드가 없었다.
- `PermissionDenied`나 `PermissionRequest` 건수는 실제 가드 거부의 유효한 대리 지표가 아니었다.
- 기존 실측(v0 수집 6일 + 소급 발췌 2건)에서 "같은 가드의 다세션 자연 발동" 조건을 충족한 가드는 0개였다. 확인된 것은 서로 다른 가드의 발동 각 1회이고, 그중 한 가드는 이미 제거됐다. 자연 발동 빈도가 낮을 수 있다는 사실이 운영 빈도 가설을 관찰로 검증해야 하는 이유다.

### 미검증 가설

- 구조화된 사건과 버전 고정 맥락이 없어서 가드의 유지·수정·제거 결정이 실제로 어렵다.
- 사후 기록과 두 축의 판정이 의사결정 시간, 근거 복원 노력, 또는 결정 확신을 개선한다.
- 같은 문제를 겪는 다른 지속형 가드 운영자가 존재한다. 이 가설은 v1 안에 검증 경로가 없으며, 외부 검증 전까지 미검증으로 남는다.

관찰 사실은 문제의 출발점일 뿐, 사용자 가치나 외부 수요를 증명하지 않는다.

## 4. 현재 대안

현재 현실적인 대안은 두 가지다.

1. 가드가 발동한 순간 기억에 의존해 즉시 수정하거나 무시하고, 나중에 필요하면 흩어진 오류 로그를 수동 검색한다.
2. 세션 transcript와 git 이력을 수동 대조해 사건 원문과 당시 가드 상태를 복원한다. [`docs/소급-발췌-매니페스트.md`](../소급-발췌-매니페스트.md)가 이 경로로 verbatim 복원이 가능함을 실증했다. 다만 transcript는 보존 기한이 있고, 복원은 사건당 수십 분의 수작업이며, 가드 맥락의 버전 특정은 보장되지 않는다.

이 대안들은 추가 도구가 필요 없다는 장점이 있다. Reject Bench가 가치 있으려면 적어도 다음 셋 중 하나를 실제로 개선해야 한다.

1. 유지·수정·제거 결정에 걸리는 의사결정 시간이 줄었는가
2. 당시 맥락과 근거를 다시 찾는 노력이 줄었는가
3. 결정에 대한 사용자의 확신이 높아졌는가

개선 여부는 관찰 시작 전에 선등록한 평가 양식(확신 문항·복원 소요 시간 기록)과 기준선 측정 1회(첫 자연 사건을 도구 보고서를 보기 전에 대안 2로 먼저 복원)로 판정한다. 같은 사람이 만들고 측정하고 평가하는 1인 실험의 자기측정 한계는 이것으로 제거되지 않으며, 보고서에 그대로 명시한다.

CodeRabbit, Greptile, dryforge 같은 도구는 범용 리뷰나 계약 실행을 다루므로 이번 문제의 직접 비교군이 아니다.

## 5. 판단을 두 축으로 분리한다

### 정책 일치성 — LLM의 역할

독립 LLM은 **사건 당시 버전으로 고정된 가드 맥락**과 사건 기록만 받아, 하나의 질문에 답한다: **이 차단이 명시 정책상 옳았는가.**

- `correct_block`: 명시 정책상 막는 것이 옳았고, 명시 예외에 해당하지 않는다
- `incorrect_block`: 명시 정책 또는 명시 예외에 비추어 막지 말았어야 했다
- `insufficient_context`: 주어진 근거만으로 판단할 수 없다

질문을 "차단의 옳음" 하나로 두는 이유: 예외에 해당하는 행동은 "정책 문면은 위반"과 "막지 말았어야 함"이 동시에 성립해, 위반 여부를 묻는 라벨로는 두 값이 배타적이지 않게 되기 때문이다.

LLM은 정책의 유용성, 사용자의 만족, 가드의 존폐를 결정하지 않는다. 미래 사건이나 집계 결과도 입력으로 받지 않는다.

### 실제 유용성 — 사용자의 역할

사용자는 같은 사건이 실제 작업에 도움이 됐는지 표시한다.

- `useful`: 방해를 감수할 가치가 있었다
- `unnecessary`: 실제로는 불필요한 차단이었다
- `uncertain`: 지금은 판단하기 어렵다

정책대로 막았지만 쓸모없는 가드일 수 있고, 정책 문구와 어긋났지만 우연히 도움 된 차단일 수도 있다. 따라서 두 판단을 하나의 `오탐`으로 합치지 않는다.

## 6. 목표 흐름

1. 가드 발동 시 사건을 비블로킹으로 자동 기록한다.
2. 사건은 발생 당시의 가드 버전과 맥락 해시를 참조한다.
3. 세션이 끝난 뒤 LLM이 새 운영 사건 전부를 정책 기준으로 판단한다.
4. 사용자가 같은 사건 전부를 검토해 유용성을 표시한다.
5. 여러 세션의 증거를 모아 가드별 `keep`, `modify`, `remove` 결정을 기록한다.

코딩 중에는 검토를 요구하거나 흐름을 끊지 않는다. 판단은 세션 뒤에 한다.

## 7. 운영 사건과 시험 사건

- `operation`: 실제 개발 작업 중 자연스럽게 발생한 사건
- `test`: 기록기·어댑터·판정 파이프라인을 검증하려고 의도적으로 발동한 사건
- `unknown`: 생성 시점에 출처를 확정할 수 없는 사건

출처는 사건 생성 시점에 다음 규칙으로 정한다.

1. 세션 test 플래그가 켜져 있으면 항상 `test`다. 강제 발동, fixture, 스모크, E2E는 모두 test 플래그를 켜고 실행한다.
2. 플래그가 없으면 `operation`이며, `origin_evidence`에 기본값 상속임을 남긴다.
3. 생성 시점에 실행 맥락 정보를 얻지 못한 경우만 `unknown`이다.

세션 뒤 검토에서 본인이 시험·강제 발동이었음을 확인하면 사유 있는 수정 기록으로 `test` 강등을 허용한다 — 지표를 보수적으로 만드는 방향의 정정이다. `unknown`을 사후에 운영 사건으로 조용히 승격할 수 없고, 정정이 필요하면 원본을 덮지 않는 수정 기록을 남긴다. 출처는 운영자 본인의 선언에 기반하며 독립 검증 신호가 없다 — 이 한계는 보고서에 명시한다.

시험 사건은 기술 완성도를 검증할 수 있지만 다음 증거로는 쓸 수 없다.

- 문제가 실제 운영에서 발생한다는 증거
- 사용자 가치 증거
- 운영 지표의 분자나 분모

## 8. 최소 성공과 지표

### 최소 사용자 가치 증거

> **같은 지속형 가드가 여러 세션에서 자연 발동 → 버전 고정 맥락으로 LLM 정책 판정 → 사용자 유용성 검토 → 근거와 함께 유지·수정·제거 결정 1건**

자연 운영 사건이 없으면 기술 파이프라인이 모두 통과해도 사용자 가치는 미검증이다. 흐름 완수 자체는 가치 증명이 아니다 — 가치 개선 여부는 4절의 선등록 양식과 기준선 비교로 따로 판정한다.

### 대표 지표

**증거 기반 결정 완료율**

`근거와 결정 사유를 기록한 keep/modify/remove 가드 수 / 판정 가능한 가드 수`

판정 가능한 가드: 서로 다른 둘 이상의 `operation` 세션 사건이 있고, 그 사건들이 참조하는 GuardSpec이 존재하며, 그 사건들의 정책 판정과 유용성 검토가 모두 확정값인 가드. 분자는 분모의 부분집합으로만 센다 — 발동 사건이 없는 가드에 대한 결정은 기록할 수 있으나 별도 표기하고 이 지표에 넣지 않는다.

백분율만 쓰지 않고 항상 원수 `N/D`를 함께 쓴다. 분모가 0이면 `미검증`으로 표시한다.

### 진단 지표

- 정책 불일치율 = `incorrect_block / 정책 판정이 확정값인 운영 사건`
- 사용자 불필요 차단율 = `unnecessary / 유용성 검토가 확정값인 운영 사건`
- LLM-사용자 불일치율 = 정책 일치성과 사용자 유용성의 방향이 어긋난 운영 사건 / 두 판단이 모두 확정값인 운영 사건

`insufficient_context`와 `uncertain`은 기록된 보류값으로, 판정·검토 레코드 자체가 없는 미처리와 구분한다. 보류값과 미처리는 각 비율의 분모에서 제외하되, 각각의 건수와 최장 대기 기간을 함께 표시한다. 소표본에는 통계적 일반화 표현을 쓰지 않는다.

### 단측 증거의 한계

이 도구의 증거는 발동한 사건뿐이다. 가드가 놓친 것 — 발동했어야 하는데 하지 않은 실패 — 은 관측 밖이다. 따라서 `keep` 결정은 "문제가 없다"와 "가드가 죽어 있다"를 구분하지 못하고, 정책 불일치율은 과잉 차단만 재는 단측 지표다. 이 한계는 모든 보고서에 병기한다.

## 9. 반증과 중단 조건

관찰을 시작하기 전에 관찰 종료 조건, 평가 질문, 응답 양식을 고정한다. 관찰 프로토콜 문서 자체도 append 전용이며, 변경은 사유 있는 수정 기록으로만 한다. 현재는 근거 없는 숫자 임계값을 만들지 않는다.

1. 관찰 기간 동안 같은 가드의 자연 발동이 여러 세션에서 없으면 **운영 빈도 가설 미검증**으로 종료한다.
2. 기록과 판정이 의사결정 시간, 근거 복원 노력, 결정 확신 중 아무것도 개선하지 못하면 **해법 가치 가설 실패**로 본다.
3. 세션 뒤 전수 검토 부담이 얻는 가치보다 크면 **채택 가설 실패**로 본다.
4. `insufficient_context`가 지배적이면 **캡처 설계 실패**로 보고, 행동 뼈대·비밀 제거 계약을 재설계한다.

관찰 종료 선언은 배타적 4지선다가 아니라 두 축으로 한다. 기술 상태(완료/미완)와 가치 상태(검증/미검증/가치 실패/채택 실패)를 각각 선언해, "흐름은 완수했으나 가치 개선은 없었다" 같은 조합을 표현할 수 있게 한다.

실패 결과도 삭제하거나 기술 성공으로 덮지 않는다.

## 10. 주장 범위

v1이 말할 수 있는 최대 범위는 다음뿐이다.

> **내 저장소에서 사라지던 가드 발동을 증거 기반 가드 결정으로 바꾸는 개인 도구 실험.**

v1에서 주장하지 않는 것:

- 다른 개발자나 팀에도 유용하다
- AI 생성 코드의 품질이나 팀 생산성을 높인다
- 시장 수요가 검증됐다
- 공개·재현 가능성이 수요를 증명한다
- 범용 코드 리뷰 도구보다 낫다

## 11. 왜 지금, 외부 검증은 언제인가

수집기 v0가 실제 가드 거부를 놓쳤다는 사실을 확인했고, 폐기된 v6 준비 구현(당시 라벨 "T1" — 현행 `plan.md`의 T1과는 다른 작업이다)을 통해 구조화 형식의 가능성까지 확인했다. 따라서 지금부터 생기는 새 운영 사건은 이전처럼 사라지지 않게 설계할 수 있다. 이것이 현재의 내부 `왜 지금`이다. 시장 변화나 채용 공고는 부차적 배경일 뿐이다.

여기에 2026-08-28 인터뷰가 시점 하나를 더했다: 관측 무대인 reply-gate 배포 작업이 임박해 있고, 기록기가 서기 전에 그 작업을 하면 그 세션들의 가드 발동은 다시 유실된다. 그래서 기록기(T1~T3)가 관측 무대보다 먼저다.

먼저 한 저장소 운영자의 자연 운영 흐름 전체를 한 번 완성한다. 그 뒤에만 이미 지속형 가드를 운영하는 독립 사용자에게 같은 흐름을 시험한다. 실제 외부 사용 전에는 일반화하지 않는다.

## 12. v7 설계에 주는 결론

- 공개 원장·push 증명·대시보드는 v1 핵심에서 제외한다.
- 소급 2건과 강제 발동은 기술 참고 자료일 뿐 사용자 가치 증거가 아니다.
- 단일 오탐률을 폐기하고 정책 일치성·사용자 유용성·수명주기 결정을 분리한다.
- 가드 맥락은 사건보다 먼저 버전 고정돼야 한다.
- 관측 대상은 실존 가드 2종으로 고정하고, 기록 저장은 reject-bench 저장소의 로컬 비공개 경로에 중앙화한다.
- 기록기(T3)가 서기 전에는 관측 무대(reply-gate 배포 작업)를 시작하지 않는다.
- 판정 enum은 차단의 옳음을 묻는 `correct_block | incorrect_block | insufficient_context`다.
- 원시 운영 기록은 로컬·비공개를 기본값으로 하고 적재 시점에 비밀을 제거한다.
- MCP·증거 조회 표면은 v1 완료 조건이 아니며, 관찰 대기 구간의 선택 증분(T7)으로만 다룬다.
- 새 구현은 v7 계약 승인 뒤 백지에서 시작한다.
- 기존 준비 구현은 재사용하지 않는다. git 이력과 실측 원천은 보존하고, 승인 뒤 전용 정리 커밋에서 구현 전용 파일만 폐기한다.
